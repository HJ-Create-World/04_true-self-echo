# DOC_STANDARD · 文档编写规范

> **要写新文档时读这份。** 它规定了目录归属、命名规则、frontmatter 字段、以及 6 类文档的模板。

---

## 一、为什么要有规范（问题机制）

文档膨胀对 AI 辅助开发的伤害不是"找不到"，而是**四个更隐蔽的机制**：

### 机制 1：检索阶段——LLM 没有"时效"和"权威"概念
向量检索和关键词检索都只看**语义相似度**。一份 2026-09 的正确文档和一份 2026-07 的过期文档，如果都在讲同一件事，**检索器无法分辨哪个更新**。它会同等对待。

### 机制 2：排序阶段——干扰项恰好最难区分
同一事实的多个版本，语义相似度**极高**。这正是 rerank 模型最不擅长的情形（它擅长区分"相关"和"不相关"，不擅长区分"两个都很相关但一个过期"）。

### 机制 3：冲突阶段——最危险的是"合成中间版本"
模型拿到两个矛盾版本时，有两种失败方式：
- **随意选一个**（容易发现，运气好选对）
- 🔴 **合成一个不存在的中间版本** —— 这个**最危险**，因为它读起来完全合理、语法通顺、逻辑自洽，**人很难察觉它是编的**

### 机制 4：固化阶段——污染会自我繁殖
错误的合成结果被写进新文档 → 下一轮检索命中三个版本 → 冲突加剧。

### 机制 5：长度本身就在消耗可靠性
2025 年 Chroma 对 18 个模型的实测显示：**上下文长度增加本身就会降低输出可靠性**，连"复制重复词"这种平凡任务都退化。
**所以"全量喂文档"不是"找不到"的问题，而是在别处悄悄变笨。**

> **结论：解决方式不是"写得更好"，而是"减少重复"。**
> 单一信息源不是洁癖，是防止上述四条机制的唯一有效手段。

## 二、目录归属规则

**一份文档该放哪？按「它回答什么问题」决定，不按「它是什么格式」决定。**

| 目录 | 回答什么问题 | 典型内容 | 变更频率 |
|---|---|---|---|
| `00_meta/` | 怎么找到别的文档？ | 索引、状态、术语、规范 | 状态高，其余低 |
| `01_product/` | **做什么**？给谁做？不做哪些？ | 定位、需求、计划 | 低（定稿后罕见改动） |
| `02_decisions/` | **为什么**这么做？ | ADR，一条一个文件 | **只增不改** |
| `03_specs/` | **怎么做**？数据长什么样？ | schema、接口、算法 | 中 |
| `04_lab/` | **验证过什么**？测到了什么？ | 实验报告、原始数据 | 只增不改 |
| `05_research/` | **别人**怎么做的？ | 竞品、市场、开源盘点 | 低 |
| `06_ops/` | **怎么动手**？ | 规范、Runbook | 中 |
| `_archive/` | （不回答任何问题） | 已废弃内容 | 冻结 |

### 判断流程

```
这份内容回答的是…
├─ 项目现在怎么样了？          → 00_meta/STATUS.md（更新，不新建）
├─ 我们要做什么？              → 01_product/
├─ 我们为什么选了这个方案？    → 02_decisions/（新建一个 Dxxx）
├─ 这个数据结构长什么样？      → 03_specs/
├─ 我们测到了什么？            → 04_lab/
├─ 外部项目/市场是什么情况？   → 05_research/
├─ 具体怎么操作？              → 06_ops/
└─ 以上都不是（历史遗留）      → 先想清楚，再决定放哪
```

> ⚠️ **如果你觉得"这份内容哪里都不放不合适"，通常说明它该被拆成两份，或者它其实属于已有的某份文档。**
> **不要为此新建目录。**

## 三、命名规则

### 3.1 目录
```
两位数字_英文小写_下划线分隔
例：00_meta  01_product  04_lab
```
**为什么用数字前缀**：让目录按"信息层级"排列而非字母序，且一眼看出加载顺序。

### 3.2 文件
```
决策记录：  D{三位编号}-{中文短名}.md        例：D003-架构选型.md
实验报告：  E{编号}-{中文短名}.md            例：E1-纯台词提取.md
产品文档：  {英文大写短名}.md                例：SPEC.md / PLAN.md
操作文档：  {英文大写短名}.md                例：RUNBOOK.md
调研报告：  {中文短名}.md                    例：竞品-Distilly.md
```

### 3.3 三条硬规则
1. **不要用"最终版""新版""v2""旧"这类文件名** —— 版本靠 git 管，不靠文件名
2. **不要用日期当文件名** —— 日期放 frontmatter 的 `updated` 字段
3. **中文文件名允许，但要短（≤12 字）** —— 太长在终端和日志里会被截断

## 四、Frontmatter 规范（必填）

每份文档必须以这个开头：

```yaml
---
title: 人类可读的标题
type: adr | spec | lab-report | research | guide | index | status | product | runbook | plan
status: active | draft | superseded | archived
updated: YYYY-MM-DD
owner: HJ
related: [相关文档的编号或文件名]
---
```

**`type` 取值说明**：

| type | 用于 | 例 |
|---|---|---|
| `index` | 索引 / 登记表 | `INDEX.md`、`04_lab/README.md` |
| `status` | 只讲进度的文件 | `STATUS.md` |
| `product` | 产品定义、需求、计划 | `PRODUCT.md` / `SPEC.md` / `PLAN.md` |
| `adr` | 决策记录 | `02_decisions/Dxxx-*.md` |
| `spec` | 技术规范 / 数据结构 | `03_specs/*.md` |
| `lab-report` | 实验报告与原始数据 | `04_lab/**/*.md` |
| `research` | 外部调研 | `05_research/*.md` |
| `guide` | 操作规范 / 工具清单 | `DEV_STANDARD.md` / `TOOLING.md` |
| `runbook` | 可执行的操作手册 | `RUNBOOK.md` |
| `plan` | 执行计划书（区别于 product 的长期计划） | 实验执行卡片 |
| `agent-entry` | 给 AI 协作者的入口说明 | `AGENTS.md` |

> ⚠️ **不要自创 type 值。** 需要新的类型时，先在此表登记再加使用。

| 字段 | 必填 | 说明 |
|---|---|---|
| `title` | ✅ | 人看的标题，可以和文件名不同 |
| `type` | ✅ | 决定它属于哪类文档 |
| `status` | ✅ | **最重要**。决定它能不能被当依据 |
| `updated` | ✅ | 最后更新日期 |
| `owner` | ✅ | 负责人 |
| `related` | ⬜ | 相关文档，便于横向跳转 |

### ⚠️ status 的语义（必须准确）

| status | 含义 | AI 该怎么做 |
|---|---|---|
| `active` | 当前有效 | ✅ 可以作为依据 |
| `draft` | 草稿，未经确认 | ⚠️ 可参考，**不可作为依据** |
| `superseded` | 已被取代 | ❌ 不要用，去看它 `related` 指向的新文档 |
| `archived` | 已归档 | ❌ **绝对不要用** |

### ⚠️ 关键提醒：frontmatter 对 LLM 不是自动可见的

AGENTS.md 官方明确**不推荐**依赖 YAML frontmatter。所以：
- **`AGENTS.md` 里必须显式写"去读 status 字段"**（已写）
- 否则这层元数据对 LLM 是**隐形的**，等于没写

## 五、文档结构要求

### 5.1 开头的导语块（必需）

正文第一块必须是：

```markdown
> **什么时候读这份文档**：<一句话说清用途和边界>
>
> **它不是**：<一句话说清它不管什么，防止被误用>
>
> **它能回答**：<列 2-4 个具体问题>
```

**为什么**：让 LLM 能在**不读全文**的情况下判断这份文档相不相关。这是"按需加载"的前提。

### 5.2 结论先行

第一段（导语之后）就给结论。细节放后面。

### 5.3 禁止无法验证的形容词

| ❌ 不许写 | ✅ 要写 |
|---|---|
| 有韵律感 | 句子平均 12.3 字，跨度 8.4–18.6 字 |
| 很温柔 | 对方低落时，先否定担忧，再给"允许不动"的许可 |
| 效果不错 | 六维评分 22/30，反差层次 3/5 |
| 性能良好 | P95 延迟 120ms |

> **自检方法**：把这句话给一个没读过素材的人，他能照着执行/复现吗？不能 → 重写。

### 5.4 不确定就写"未获取"

**绝对不要编造**数据、链接、星数、日期、引用。
用「未获取」「证据不足」「推断」明确标注不确定的部分。

## 六、六类文档模板

### 模板 1：ADR（架构决策记录）

**什么时候用**：做了一个以后可能被质疑的技术/产品决策。

**关键**：ADR **只增不改**。决策变更时，新建一份 `superseded by` 它。

```markdown
---
title: D{编号} · {决策短名}
type: adr
status: active
updated: YYYY-MM-DD
owner: HJ
related: [相关文档]
supersedes: (可选) 被本决策取代的编号
---

# D{编号} · {决策短名}

> **什么时候读这份文档**：当你想推翻这个决策、或想知道当初为什么这么定。
>
> **它不是**：实施细节（那是 `03_specs/`）。
>
> **它能回答**：为什么选 A 不选 B？当时考虑了哪些方案？什么情况下这个决策会失效？

---

## 状态
✅ 已定 / ⚠️ 待定 / ❌ 已废弃

## 背景
（是什么问题逼我们做这个决策？）

## 候选方案

| 方案 | 优点 | 缺点 |
|---|---|---|
| A | | |
| B | | |

## 决策
**选 X。**（一句话）

## 理由
（为什么 X 比其他好？要有可验证的依据，不要"感觉更好"）

## 代价
（选了这个，我们放弃了什么？这是诚实的部分，不要只写好处）

## 什么情况下要重审
（触发条件。例：「如果 X 增长到 Y，本决策失效」）
```

---

### 模板 2：实验报告（Lab Report）

**什么时候用**：做了一次验证，有假设、有数据、有结论。

**关键**：原始数据**只增不改**。结论错了就新建一份，或在新实验里注明修正。

```markdown
---
title: E{编号} · {实验短名}
type: lab-report
status: active
updated: YYYY-MM-DD
owner: HJ
related: [对照实验的编号]
---

# E{编号} · {实验短名}

> **什么时候读这份文档**：当你要引用这个结论，或要设计类似实验时。
>
> **它不是**：结论汇总（那是 `04_lab/README.md`）。
>
> **它能回答**：测了什么？怎么测的？数字是多少？结论可靠吗？

---

## 一、测试设置

| 项 | 值 |
|---|---|
| 假设 | （要验证什么） |
| 投料/输入 | （具体文件路径 + 大小） |
| 方法 | （怎么做的） |
| 对照组 | （如果有） |

## 二、过程

（具体怎么执行的，可复现）

## 三、结果

（原始数据。**表格优先**，数字要具体）

## 四、结论

（数据说什么？）

## 五、局限与污染

⚠️ **这一节必须写。**
- 样本量够吗？
- 有没有自我批卷偏差？
- 有没有污染源（如"考题带答案"）？
- 哪些结论**不能**从这个实验得出？

## 六、对产品的影响

（这个结论改变了什么设计决策？）
```

**什么时候用**：定义数据结构、接口、模块设计。

> **它不是**：需求（那是 `01_product/SPEC.md`）。

> **它能回答**：字段有哪些？类型是什么？约束是什么？

  field: type;  // 说明

| 字段 | 类型 | 必填 | 约束 | 说明 |

| | | | | |

| 方法 | 入参 | 返回 | 说明 |

| | | | |

### 模板 6：项目入口（AGENTS.md 类）

**什么时候用**：给 AI 看的入口文件。一个项目只有一个。

**已存在于 `00_meta/AGENTS.md`**，结构见该文件。要点：
- **按任务类型列"读什么"**，不要列文件清单
- **写清硬规则**（单一信息源、status 检查、别名不要引用 archive）
- **保持短** —— 它每次都被读，太长会挤占上下文

## 七、生命周期管理

### 7.1 文档状态流转

```
draft ──确认──> active ──被取代──> superseded ──> archived
  │                 │
  └──废弃───────────┘
```

### 7.2 归档触发条件

出现任一条件，**考虑归档**：

| 条件 | 例 |
|---|---|
| 结论已被新实验推翻 | 第一轮 Phase 0 的"提取质量决定上限"被第二轮推翻 |
| 内容已拆分到别处 | `PHASE0_人格提取验证.md` 拆到 `04_lab/` + `STATUS.md` |
| 描述的功能已砍掉 | 某个被 Non-Goals 排除的设计 |
| 3 个月未被任何文档引用 | 需主动检查 `related` 引用情况 |

### 7.3 废弃处理（关键：物理隔离，不只是打标记）

⚠️ **只打「已废弃」横幅是不够的**，原因：
1. 横幅**未必在检索片段里**（LLM 只看到中间一段，看不到顶部横幅）
2. 废弃文档与有效文档的**语义相似度一样高**，检索器无法区分

**三种有效做法**（按推荐度）：

| 做法 | 说明 | 推荐度 |
|---|---|---|
| **移入 `_archive/`** | 物理隔离，目录名本身就是信号 | ⭐⭐⭐ |
| **改造成「墓碑页」** | 删掉正文，只留横幅 + 取代者 + "改了什么" | ⭐⭐ |
| **文件名加前缀** | `DEPRECATED-xxx.md` | ⭐ |

**墓碑页模板**：
```markdown
---
title: {原名}（已废弃）
type: index
status: archived
updated: YYYY-MM-DD
---

# ⚠️ 本文档已废弃

**废弃时间**：YYYY-MM-DD
**取代者**：`{新文档路径}`
**为什么废弃**：{一句话}
**改了什么**：{关键差异，让人知道要不要去看新的}

<!-- 正文已删除，避免被误引用 -->
```

### 7.4 引用规则

| 场景 | 写法 |
|---|---|
| 文档间引用 | 相对路径：`见 02_decisions/D003-架构选型.md` |
| 引用具体段落 | 加小节号：`见 SPEC.md §6.2` |
| 引用外部资料 | 完整 URL 或文件路径 + 行号 |
| **引用 `_archive/`** | ❌ **禁止** |

## 八、写新文档前的自检清单

写之前逐条过：

- [ ] 这个内容**已经在别的文档里**了吗？（先查 `INDEX.md` 的信息归属表）
- [ ] 如果已存在 → **去改那一处**，不要新建
- [ ] 如果不存在 → 它回答的是"做什么/为什么/怎么做/测到什么/别人怎么做/怎么操作"哪一类？
- [ ] 对应的目录是？
- [ ] 文件名符合命名规则吗？（无"最终版""v2""日期"）
- [ ] frontmatter 六个字段填齐了吗？`status` 标对了吗？
- [ ] 开头导语块写了吗？（什么时候读 / 不是什么 / 能回答什么）
- [ ] 有没有无法验证的形容词？
- [ ] 有没有编造的数据？
