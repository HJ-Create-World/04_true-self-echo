# DOC_STANDARD · 文档编写规范

> **要写新文档时读这份。** 它规定了目录归属、命名规则、frontmatter 字段、以及 6 类文档的模板。

---

## 一、为什么要有规范（问题机制）

文档膨胀对 AI 辅助开发的伤害不是"找不到"，而是**四个更隐蔽的机制**：

### 机制 1：检索阶段——LLM 没有"时效"和"权威"概念
向量检索和关键词检索都只看**语义相似度**。一份 2026-09 的正确文档和一份 2026-07 的过期文档，如果都在讲同一件事，**检索器无法分辨哪个更新**。它会同等对待。

### 机制 2：排序阶段——干扰项恰好最难区分
同一事实的多个版本，语义相似度**极高**。这正是 rerank 模型最不擅长的情形（它擅长区分"相关"和"不相关"，不擅长区分"两个都很相关但一个过期"）。

### 机制 3：冲突阶段——最危险的是"合成中间版本"
模型拿到两个矛盾版本时，有两种失败方式：
- **随意选一个**（容易发现，运气好选对）
- 🔴 **合成一个不存在的中间版本** —— 这个**最危险**，因为它读起来完全合理、语法通顺、逻辑自洽，**人很难察觉它是编的**

### 机制 4：固化阶段——污染会自我繁殖
错误的合成结果被写进新文档 → 下一轮检索命中三个版本 → 冲突加剧。

### 机制 5：长度本身就在消耗可靠性
2025 年 Chroma 对 18 个模型的实测显示：**上下文长度增加本身就会降低输出可靠性**，连"复制重复词"这种平凡任务都退化。
**所以"全量喂文档"不是"找不到"的问题，而是在别处悄悄变笨。**

> **结论：解决方式不是"写得更好"，而是"减少重复"。**
> 单一信息源不是洁癖，是防止上述四条机制的唯一有效手段。

## 二、目录归属规则

**一份文档该放哪？按「它回答什么问题」决定，不按「它是什么格式」决定。**

| 目录 | 回答什么问题 | 典型内容 | 变更频率 |
|---|---|---|---|
| `00_meta/` | 怎么找到别的文档？ | 索引、状态、术语、规范 | 状态高，其余低 |
| `01_product/` | **做什么**？给谁做？不做哪些？ | 定位、需求、计划 | 低（定稿后罕见改动） |
| `02_decisions/` | **为什么**这么做？ | ADR，一条一个文件 | **只增不改** |
| `03_specs/` | **怎么做**？数据长什么样？ | schema、接口、算法 | 中 |
| `04_lab/` | **验证过什么**？测到了什么？ | 实验报告、原始数据 | 只增不改 |
| `05_research/` | **别人**怎么做的？ | 竞品、市场、开源盘点 | 低 |
| `06_ops/` | **怎么动手**？ | 规范、Runbook | 中 |
| `notes/` | （不回答任何问题） | 临时草稿、想法碎片 | 任意 |
| `_archive/` | （**已移出主检索路径**） | 两类：① 归档资产（素材/Prompt/方法论，仍可引用）② 过程记录（旧测试报告，只作历史追溯） | 冻结 |

### 关于 `notes/`

`notes/` 位于**仓库根目录**（不是 `docs/` 下），是**临时草稿区**：

| 项 | 规定 |
|---|---|
| 用途 | 记想法碎片、半成品草稿、待整理的材料，写完随时可丢 |
| frontmatter | ❌ **不需要**（这是它存在的意义 —— 降低记录门槛） |
| 命名 | ❌ 不受 §三 命名规则约束 |
| 登记 | ❌ **不进 `INDEX.md`**，不算文档体系的一部分 |
| AI 依据 | ❌ **不可作为依据**（内容未经验证、可能过期） |
| 成熟之后 | 内容一旦稳定 → 按 §二 判断流程挪进正式目录，补齐 frontmatter 并登记 INDEX |

> ⚠️ **`notes/` 里不放长期有价值的内容。** 判断标准：如果这份内容三个月后还有人要读，它就不该在 `notes/`。
>
> 📌 **现状**：截至 2026-09-17，`notes/` 为空目录（保留备用）。

### 判断流程

```
这份内容回答的是…
├─ 项目现在怎么样了？          → 00_meta/STATUS.md（更新，不新建）
├─ 我们要做什么？              → 01_product/
├─ 我们为什么选了这个方案？    → 02_decisions/（新建一个 Dxxx）
├─ 这个数据结构长什么样？      → 03_specs/
├─ 我们测到了什么？            → 04_lab/
├─ 外部项目/市场是什么情况？   → 05_research/
├─ 具体怎么操作？              → 06_ops/
├─ 还没想清楚，只是草稿？      → notes/（不进文档体系）
└─ 以上都不是（历史遗留）      → 先想清楚，再决定放哪
```

> ⚠️ **如果你觉得"这份内容哪里都不放不合适"，通常说明它该被拆成两份，或者它其实属于已有的某份文档。**
> **不要为此新建目录。** 唯一的例外是 `notes/`（见上）—— 但它不承载任何长期内容。

### 关于项目根 `README.md`

**项目根 `README.md` 是对外门面，不属于 `docs/` 文档体系。**

| 项 | 规定 |
|---|---|
| 读者 | GitHub 访客 / 第一次点进仓库的人（**不是 AI**） |
| 职责 | 一段话说清「这是什么」+ 从哪开始读 + 技术栈 |
| frontmatter | ✅ **仍要写**（六个字段同 §四），保持一致风格 |
| 与 `PRODUCT.md` 的区别 | `README.md` 是**门面**（短、对外、稳定）；`PRODUCT.md` 是**内容**（全貌、随项目演进） |
| 目录归属 | 不受 §二 目录树约束 —— 它必须待在仓库根，否则 GitHub 不渲染 |

> ⚠️ **`README.md` 不复制进度信息。** 任何"现在到哪一步了"都只写一句 + 指向 `00_meta/STATUS.md`。

## 三、命名规则

### 3.1 目录
```
两位数字_英文小写_下划线分隔
例：00_meta  01_product  04_lab
```
**为什么用数字前缀**：让目录按"信息层级"排列而非字母序，且一眼看出加载顺序。

### 3.2 文件
```
决策记录：  D{三位编号}-{中文短名}.md        例：D003-架构选型.md
实验报告：  E{编号}-{中文短名}.md            例：E1-纯台词提取.md
产品文档：  {英文大写短名}.md                例：SPEC.md / PLAN.md
操作文档：  {英文大写短名}.md                例：RUNBOOK.md
调研报告：  {中文短名}.md                    例：竞品-Distilly.md
```

### 3.3 三条硬规则
1. **不要用"最终版""新版""v2""旧"这类文件名** —— 版本靠 git 管，不靠文件名
2. **不要用日期当文件名** —— 日期放 frontmatter 的 `updated` 字段
3. **中文文件名允许，但要短（≤12 字）** —— 太长在终端和日志里会被截断

## 四、Frontmatter 规范（必填）

每份文档必须以这个开头：

```yaml
---
title: 人类可读的标题
type: adr | spec | lab-report | research | guide | index | status | product | runbook | plan
status: active | draft | superseded | archived
updated: YYYY-MM-DD
owner: HJ
related: [相关文档的编号或文件名]
---
```

**`type` 取值说明**：

| type | 用于 | 例 |
|---|---|---|
| `index` | 索引 / 登记表 | `INDEX.md`、`04_lab/README.md` |
| `status` | 只讲进度的文件 | `STATUS.md` |
| `product` | 产品定义、需求、计划 | `PRODUCT.md` / `SPEC.md` / `PLAN.md` |
| `adr` | 决策记录 | `02_decisions/Dxxx-*.md` |
| `spec` | 技术规范 / 数据结构 | `03_specs/*.md` |
| `lab-report` | 实验报告与原始数据 | `04_lab/**/*.md` |
| `research` | 外部调研 | `05_research/*.md` |
| `guide` | 操作规范 / 工具清单 | `DEV_STANDARD.md` / `TOOLING.md` |
| `runbook` | 可执行的操作手册 | `RUNBOOK.md` |
| `plan` | 执行计划书（区别于 product 的长期计划） | 实验执行卡片 |
| `agent-entry` | 给 AI 协作者的入口说明 | `AGENTS.md` |

> ⚠️ **不要自创 type 值。** 需要新的类型时，先在此表登记再加使用。

| 字段 | 必填 | 说明 |
|---|---|---|
| `title` | ✅ | 人看的标题，可以和文件名不同 |
| `type` | ✅ | 决定它属于哪类文档 |
| `status` | ✅ | **最重要**。决定它能不能被当依据 |
| `updated` | ✅ | 最后更新日期 |
| `owner` | ✅ | 负责人 |
| `related` | ⬜ | 相关文档，便于横向跳转 |

### ⚠️ status 的语义（必须准确）

| status | 含义 | AI 该怎么做 |
|---|---|---|
| `active` | 当前有效 | ✅ 可以作为依据（**注意：在 `_archive/` 下的 `active` 仍有效，见 §7.5**） |
| `draft` | 草稿，未经确认 | ⚠️ 可参考，**不可作为依据** |
| `superseded` | 已被取代 | ❌ 不要用，去看它 `related` 指向的新文档 |
| `archived` | 已归档，整体失效 | ❌ **绝对不要用** |

### ⚠️ `superseded` 与 `archived` 的区别（必须分清）

这两个词都表示「不要用」，但**对文件位置的要求相反**：

| | `superseded` | `archived` |
|---|---|---|
| 中文 | **被取代** | **已归档** |
| 位置 | **留在原位**，不移动 | **必须物理移入 `_archive/`** |
| 为什么留下 | 仍有历史引用价值，或**部分内容仍然有效** | 整体失效，只作历史留存 |
| 典型场景 | 新方案只覆盖了旧文档的一部分；旧文档里还有别处没有的数据 | 结论被推翻、功能已砍掉、内容已完全拆分到别处 |
| 正文 | **保留**（否则历史引用会断链） | 删掉，只留墓碑页（见 §7.3） |
| AI 处理 | ❌ 不作为依据，但**可以追溯它引用的具体段落** | ❌ 绝对不用，连追溯都不做 |

> 🔴 **「只打 `archived` 标签但不移动」= 标签失效。**
> 原因见 §7.3：横幅未必出现在检索片段里，而 `_archive/` **目录名本身才是信号**。
> 只改 frontmatter 而不动位置，等于丢掉了唯一的物理隔离手段。
>
> **自检**：`status: archived` 的文件**必须**在 `_archive/` 下；但 `_archive/` 下的文件
> **不一定**是 `archived`（`active` 的归档资产也放在那里，见 §7.5）。
>
> 📌 **完整规则（含「归档资产 vs 过程记录」的两分法与引用写法）见 §7.5。**

### ⚠️ 关键提醒：frontmatter 对 LLM 不是自动可见的

AGENTS.md 官方明确**不推荐**依赖 YAML frontmatter。所以：
- **`AGENTS.md` 里必须显式写"去读 status 字段"**（已写）
- 否则这层元数据对 LLM 是**隐形的**，等于没写

## 五、文档结构要求

### 5.1 开头的导语块（必需）

正文第一块必须是：

```markdown
> **什么时候读这份文档**：<一句话说清用途和边界>
>
> **它不是**：<一句话说清它不管什么，防止被误用>
>
> **它能回答**：<列 2-4 个具体问题>
```

**为什么**：让 LLM 能在**不读全文**的情况下判断这份文档相不相关。这是"按需加载"的前提。

### 5.2 结论先行

第一段（导语之后）就给结论。细节放后面。

### 5.3 禁止无法验证的形容词

| ❌ 不许写 | ✅ 要写 |
|---|---|
| 有韵律感 | 句子平均 12.3 字，跨度 8.4–18.6 字 |
| 很温柔 | 对方低落时，先否定担忧，再给"允许不动"的许可 |
| 效果不错 | 六维评分 22/30，反差层次 3/5 |
| 性能良好 | P95 延迟 120ms |

> **自检方法**：把这句话给一个没读过素材的人，他能照着执行/复现吗？不能 → 重写。

### 5.4 不确定就写"未获取"

**绝对不要编造**数据、链接、星数、日期、引用。
用「未获取」「证据不足」「推断」明确标注不确定的部分。

## 六、六类文档模板

### 模板 1：ADR（架构决策记录）

**什么时候用**：做了一个以后可能被质疑的技术/产品决策。

**关键**：ADR **只增不改**。决策变更时，新建一份 `superseded by` 它。

```markdown
---
title: D{编号} · {决策短名}
type: adr
status: active
updated: YYYY-MM-DD
owner: HJ
related: [相关文档]
supersedes: (可选) 被本决策取代的编号
---

# D{编号} · {决策短名}

> **什么时候读这份文档**：当你想推翻这个决策、或想知道当初为什么这么定。
>
> **它不是**：实施细节（那是 `03_specs/`）。
>
> **它能回答**：为什么选 A 不选 B？当时考虑了哪些方案？什么情况下这个决策会失效？

---

## 状态
✅ 已定 / ⚠️ 待定 / ❌ 已废弃

## 背景
（是什么问题逼我们做这个决策？）

## 选项

| 选项 | 描述 | 后果 |
|---|---|---|
| A | | |
| B | | |

> ⚠️ **只写"我们决定用 X"的决策记录是废纸。** 「选项」这一节必须写全 —— 半年后你会问「当初为什么不用 Y」。

## 决定
**采纳 X。**（一句话）

## 后果
（为什么 X 比其他好？要有可验证的依据，不要"感觉更好"）

**正面**
- 

**负面 / 代价**
- （选了这个，我们放弃了什么？这是诚实的部分，不要只写好处）

**后续维护点 / 缓解措施**
- 

## 关联
- [相关文档]（本节也可以放在文末）
```

### 模板 2：实验报告（Lab Report）

**什么时候用**：做了一次验证，有假设、有数据、有结论。

**关键**：原始数据**只增不改**。结论错了就新建一份，或在新实验里注明修正。

```markdown
---
title: E{编号} · {实验短名}
type: lab-report
status: active
updated: YYYY-MM-DD
owner: HJ
related: [对照实验的编号]
---

# E{编号} · {实验短名}

> **什么时候读这份文档**：当你要引用这个结论，或要设计类似实验时。
>
> **它不是**：结论汇总（那是 `04_lab/README.md`）。
>
> **它能回答**：测了什么？怎么测的？数字是多少？结论可靠吗？

---

## 一、测试设置

| 项 | 值 |
|---|---|
| 假设 | （要验证什么） |
| 投料/输入 | （具体文件路径 + 大小） |
| 方法 | （怎么做的） |
| 对照组 | （如果有） |

## 二、过程

（具体怎么执行的，可复现）

## 三、结果

（原始数据。**表格优先**，数字要具体）

## 四、结论

（数据说什么？）

## 五、局限与污染

⚠️ **这一节必须写。**
- 样本量够吗？
- 有没有自我批卷偏差？
- 有没有污染源（如"考题带答案"）？
- 哪些结论**不能**从这个实验得出？

## 六、对产品的影响

（这个结论改变了什么设计决策？）
```

**什么时候用**：定义数据结构、接口、模块设计。

> **它不是**：需求（那是 `01_product/SPEC.md`）。
>
> **它能回答**：字段有哪些？类型是什么？约束是什么？

### 模板 5：操作手册（Runbook）

**什么时候用**：记录可重复的操作步骤。

```markdown
---
title: {操作名} Runbook
type: runbook
status: active
updated: YYYY-MM-DD
owner: HJ
related: []

## 七、生命周期管理

### 7.1 文档状态流转

```
draft ──确认──> active ──部分失效──> superseded ──彻底失效──> archived
  │                 │                     （留在原位）        （移入 _archive/）
  └──废弃───────────┴─────────────────────────────────────────>┘
```

**三条出口的含义不同**：

| 出口 | 触发 | 文件动作 |
|---|---|---|
| `draft → active` | 内容经确认，可作依据 | 原地改 `status` |
| `active → superseded` | 被新文档部分取代，但仍有引用价值 | **原地改 `status`**，正文保留 |
| `→ archived` | 整体失效 | 改 `status` **+ 物理移入 `_archive/`** |

### 7.2 归档触发条件

出现任一条件，**考虑归档**：

| 条件 | 例 |
|---|---|
| 结论已被新实验推翻 | 第一轮 Phase 0 的"提取质量决定上限"被第二轮推翻 |
| 内容已拆分到别处 | `PHASE0_人格提取验证.md` 拆到 `04_lab/` + `STATUS.md` |
| 描述的功能已砍掉 | 某个被 Non-Goals 排除的设计 |
| 3 个月未被任何文档引用 | 需主动检查 `related` 引用情况 |

### 7.3 废弃处理（关键：物理隔离，不只是打标记）

⚠️ **只打「已废弃」横幅是不够的**，原因：
1. 横幅**未必在检索片段里**（LLM 只看到中间一段，看不到顶部横幅）
2. 废弃文档与有效文档的**语义相似度一样高**，检索器无法区分

**三种有效做法**（按推荐度）：

| 做法 | 说明 | 推荐度 | 对应 status |
|---|---|---|---|
| **移入 `_archive/`** | 物理隔离，目录名本身就是信号 | ⭐⭐⭐ | `archived` |
| **改造成「墓碑页」** | 删掉正文，只留横幅 + 取代者 + "改了什么" | ⭐⭐ | `archived` |
| **文件名加前缀** | `DEPRECATED-xxx.md` | ⭐ | `superseded` |

> ⚠️ **只有"整体失效"才走上面三种做法。** 如果旧文档里**部分内容仍然有效**（比如别人只引用了其中一节，
> 或别处没有的数据还在里面），应标 `status: superseded` 并**留在原位**，不要移走 —— 移走会打断历史引用。
> 区分标准见 §四 的 `superseded`/`archived` 对照表。

**墓碑页模板**：
```markdown
---
title: {原名}（已废弃）
type: index
status: archived
updated: YYYY-MM-DD
superseded_by: [{新文档路径}]
---

# ⚠️ 本文档已废弃

**废弃时间**：YYYY-MM-DD
**废弃原因**：{一句话}
**取代者**：`{新文档路径}`
**改了什么**：{关键差异，让人知道要不要去看新的}

## 原内容现在在哪

| 内容 | 现在在哪 |
|---|---|
| {原章节} | `{新文档路径}` §{小节} |

<!-- 正文已删除，避免被误引用 -->
```

> 📌 **模板要点**：
> - `superseded_by` 用 **frontmatter 字段**（数组），不要只写在正文里 —— 正文横幅可能不进检索片段
> - **「原内容现在在哪」表必写**：这是墓碑页唯一的实用价值，让人知道要不要去看新的
> - `type` 统一用 `index`（墓碑页本身不承载任何领域内容）

### 7.4 引用规则

| 场景 | 写法 |
|---|---|
| 文档间引用 | 相对路径：`见 02_decisions/D003-架构选型.md` |
| 引用具体段落 | 加小节号：`见 SPEC.md §6.2` |
| 引用外部资料 | 完整 URL 或文件路径 + 行号 |
| 引用 `_archive/` | ⚠️ **有条件允许，见 §7.5** |

### 7.5 归档资产的引用规则（本项目特殊，必须分清）

> **背景**：本条规则是 2026-09-17 修订的。原规则写「引用 `_archive/` ❌ 禁止」，
> 但实测活跃文档中有 **54 处**引用了 `_archive/phase0/` 的内容，且这些引用**大部分是正确的** ——
> 不是文档写错了，是规则本身定义过窄。下面把这两种情况分开。

**`_archive/` 里有两类东西，引用规则完全相反：**

| 类型 | 是什么 | status | 能不能引用 | 怎么引用 |
|---|---|---|---|---|
| **归档资产** | 素材原文、Prompt、方法论分析、可复用的实验资产 | `active`（**保持**） | ✅ **可以**，而且应该引用 | 正常写相对路径，无需特殊说明 |
| **过程记录** | 某次实验的测试报告、当时的结论、已失效的执行卡片 | `archived` / `superseded` | ❌ 不作为依据，✅ 可作历史追溯 | 必须写明「历史数据，非当前依据」 |

**区分方法（问一个问题）**：

> 「这份内容，如果今天从零重做，还需要再用一次吗？」
> - **需要**（比如角色台词素材、提取 Prompt、Prompt 缺陷诊断）→ **归档资产**，`status: active`
> - **不需要**（比如「第一轮测了 21/30」这个数字）→ **过程记录**，`status: archived`

**引用「过程记录」的正确写法**：

```markdown
✅ 正确：Phase 0 第一轮实测 21/30（历史数据，见 `_archive/phase0/测试结果-扮演.md`）
❌ 错误：当前评分标准是 21/30
❌ 错误：见 `_archive/phase0/测试结果-扮演.md`（不加限定，会被当成当前依据）
```

> 🔴 **为什么不能一刀切禁止引用**：
> 归档资产的物理位置在 `_archive/` 只是「为了减重、移出主检索路径」，
> 它的**内容有效性没有变**。如果因为路径在 `_archive/` 就禁止引用，
> `评分标准.md`（唯一信息源）里的「E1 实测 14/30」就会变成非法引用 ——
> 而那恰恰是支撑当前标准的关键证据。**规则不能要求人们删掉真话。**
>
> 反过来，**过程记录也确实不能被当成当前依据**。所以规则要按**文档类型**分，不能按**路径**分。

**`status` 与目录位置的正确组合**：

| status | 位置 | 含义 |
|---|---|---|
| `active` | 正常目录 | 当前有效，在主流检索路径上 |
| `active` | `_archive/` | **内容仍有效，但已不是高频引用对象** —— 需要时主动来取 |
| `superseded` | `原地` | 部分失效，留原位防止历史引用断链 |
| `archived` | `_archive/` | 整体失效，只作历史留存 |

> ⚠️ **自检**：`status: archived` 的文件**必须**在 `_archive/` 下；
> 但 `_archive/` 下的文件**不一定**是 `archived`。看到 `_archive/` 就假设里面的东西全废，是错的。

### 7.6 移动文件后必须修引用（含墓碑页自身）

⚠️ **本规范 §四 规则 3 要求「改完文档要查引用」，但墓碑页最容易漏 —— 因为它正是"指路"的那一页。**

**两件事必须同时做**：

| 动作 | 说明 |
|---|---|
| 1. 用 Grep 搜旧文件名 | 全库搜，找出所有引用它的地方 |
| 2. **按新位置重算相对路径** | ⚠️ 最容易错的一步 —— 见下 |

**相对路径要按「文件移动后的新层级」重算，不能沿用旧字符串：**

```
原位置 docs/04_lab/phase0/x.md
  引用 ../../03_specs/评分标准.md   → 解析为 docs/03_specs/评分标准.md ✅

移到 docs/_archive/phase0/x.md 后，同样的字符串变成：
  引用 ../../03_specs/评分标准.md   → 解析为 docs/../03_specs/... ❌ 多退了一层
  正确应写 ../../../03_specs/评分标准.md
```

> 🔴 **本项目已实际发生过这个错误**（2026-09-17 发现并修正）：
> `_archive/PHASE0_人格提取验证.md` 与 `_archive/模型实测说明.md` 两份墓碑页里，
> 「改了什么 → 现在在哪」表的路径全部指向已不存在的 `04_lab/phase0/`，
> 而 `superseded_by` 的相对路径多退了一层。
> **墓碑页的作用就是指路，路径错了这页就完全失去意义。**

**自检方法**：把墓碑页里每条路径**逐条验证存在性**（不要只看格式对不对）。

## 八、写新文档前的自检清单

写之前逐条过：

- [ ] 这个内容**已经在别的文档里**了吗？（先查 `INDEX.md` 的信息归属表）
- [ ] 如果已存在 → **去改那一处**，不要新建
- [ ] 如果不存在 → 它回答的是"做什么/为什么/怎么做/测到什么/别人怎么做/怎么操作"哪一类？
- [ ] **它是不是还只是草稿？** → 是的话放 `notes/`，不进文档体系
- [ ] 对应的目录是？
- [ ] 文件名符合命名规则吗？（无"最终版""v2""日期"）
- [ ] frontmatter 六个字段填齐了吗？`status` 标对了吗？
- [ ] 如果标了 `archived` → **文件在 `_archive/` 里吗？**（不在就是标签失效）
- [ ] 开头导语块写了吗？（什么时候读 / 不是什么 / 能回答什么）
- [ ] 有没有无法验证的形容词？
- [ ] 有没有编造的数据？
- [ ] 在 `INDEX.md` 里登记了吗？

## 九、维护本规范

**规范自己也要遵守规范。** 三条自检：

1. **目录树必须等于磁盘实际** —— 新增/删除目录时同步改 §二，否则 AI 会按错的树去找文件
2. **模板必须能直接套用** —— 每个模板的 frontmatter、导语块、章节都要是当前有效版本
3. **规范里提到的每一份文档都要存在** —— 引用了不存在的文件，等于教人去看空气
