# 项目开发规范

> **什么时候读这份文档**：要动代码之前；或项目开始发飘（文件变长、说不清某个文件在干什么、想加新功能）时。
>
> **它不是**：操作步骤（那是 `RUNBOOK.md`）也不是技术选型的结论（那是 `02_decisions/`）—— 它只给**约束和红线**，不给具体命令。
>
> **它能回答**：单文件最多多少行？什么时候必须推送？三个月后想不起来某个文件是干什么的怎么办？

> **这份文档不只是约束本项目。它的目标是成为一份可复用的范式，
> 用于任何"个人用 AI 辅助开发"的项目，防止烂尾与失控。**
>
> 版本：v1.0
> 建立时间：2026-09-16
> 适用范围：本项目强制；其他项目建议采用并裁剪

---

## 零、这份文档要解决什么问题

### 真实的失败模式（来自实践，不是假设）

个人用 AI 做项目的典型死亡路径：

```
项目膨胀 → 代码看不懂 → 上下文爆炸 → bug 改不完 → 放弃
```

**根因只有一个**：

> **AI 的生成速度 > 人的审查速度。**

当 AI 一分钟能写 300 行代码，而你一分钟只能读懂 30 行时，
代码库以 10 倍速度超过你的理解边界。到了某个点，你打开项目会感到
**陌生** —— 那一刻，项目就已经死了，只是还没埋。

**所以本规范的所有条款，都服务于同一个目标**：

> **提升审查能力，而不是提升生成速度。**

## 一、根本原则

### 原则 1：架构由人定，实现由 AI 写

| ✅ 正确 | ❌ 错误 |
|---|---|
| 你定义数据结构、模块划分、接口契约 | 让 AI "帮我设计一个架构" |
| AI 在你定的框架里填空 | AI 自由发挥，你事后理解 |
| 你能画出系统的框图 | 你只能说出"它大概是个聊天应用" |

**判断方法**：如果你不能用一张图画出这个项目的结构，说明架构不是你的。

### 原则 2：一个项目只学一样新东西

**新东西的额度是 1。**

| 项目 | 新东西 | 其他都用熟悉的 |
|---|---|---|
| 本项目 | **长期记忆架构 + 人格建模** | Vue3 / TS / Vite / Node 都是存量技能 |

**为什么**：学两样新东西时，出 bug 你无法判断是"新东西没学对"还是"用错了"。
**调试成本指数上升。**

> ⚠️ **已知张力：Tailwind（`D008`）**
>
> 2026-09-16 采纳了 Tailwind CSS v4（见 `02_decisions/D008-UI方案与视觉规范.md`），
> 这**看起来**是本项目的"第二样新东西"。**判定为不构成违反**，理由：
>
> | | 说明 |
> |---|---|
> | Tailwind 不是"要设计的东西" | 视觉规范（`DESIGN_STANDARD.md`）**已给定全部取值** —— 色值、圆角、阴影、动效都是照抄 |
> | 不需要"学一套 DSL 再创作" | 只是把已定的值写成 class，不存在设计决策 |
> | 反面成本更高 | 不用它，要把整份 class 词典**手工翻译成 CSS** —— 那才是真正的额外工作与漂移风险 |
>
> 📌 **本原则真正要保护的是"注意力"，不是"依赖数量"。**
> 判定标准：**新增依赖是否要求你形成新的心智模型？**
> Tailwind 在这里是**转写工具**而非**新范式** → 不占额度。
> 一个反例：引入状态机库 / 向量数据库 —— 那需要新心智模型，**占额度**。


### 原则 3：单文件 ≤ 200 行

超了就拆。这条没有例外。

**为什么是 200**：这是人能在一个屏幕上大致读完、并保持理解的量级。
超过 200 行的文件，你会开始"跳过"而不是"阅读"。

**如何执行**：
- 写完一个文件立刻看行数
- 超过 200 行的文件，按职责拆成模块
- 拆分时保持接口清晰

### 原则 4：说不出这个文件在干什么，就删掉重写

**定期自检**：随机挑一个文件，问自己：
- 它的输入是什么？
- 输出是什么？
- 为什么需要它？

**三个都答不上来 → 删掉重写。** 不要试图"先留着以后看"。

### 原则 5：README / 需求文档先写

**写不出 README，说明需求没想清。**

不是"做完再补文档"，是"文档就是设计的产物"。

### 原则 6：优先选「反馈即时」的方向

| 反馈速度 | 技术领域 |
|---|---|
| 🟢 秒级 | 前端界面、可视化、交互 |
| 🟡 分钟级 | API 调用、数据处理 |
| 🔴 小时级 | 模型训练、异步任务、状态机、数据管道 |

**为什么**：反馈越快，你能试错的次数越多，学习速度越快，
也越容易发现"这个方向不对"从而及时止损。

**本项目的选择**：纯前端可视化 —— 改一行代码，刷新就能看到结果。

### 原则 7：Non-Goals 比 Goals 更重要

**写下来你明确不做的事。** 这比"要做什么"更能防烂尾。

每次想加功能时，先看 Non-Goals 清单。**如果它在清单上，就是不做。**

## 二、版本控制规范（强制）

### 2.1 立项即 init

**项目一开始就建仓库，第一次提交放脚手架。** 不要攒到项目完成。

```powershell
cd D:\01_HJ_Work\00_Person\04_Project\<NN_项目名>
git init -b main
```

### 2.2 小步提交

**完成一个可验证的小步就提交。** 不要一次提交几十个文件。

| ✅ 好的粒度 | ❌ 坏的粒度 |
|---|---|
| 加了一个组件 | "完成第一阶段" |
| 修了一个 bug | "各种修改" |
| 写了一个模块 | "更新" |

**为什么**：回滚才有意义。一次提交 50 个文件，回滚你就丢了两周的活。

### 2.3 及时上传 GitHub（本项目明确要求）

> **这是本项目的开发纪律，不是可选项。**

**触发条件**（满足任一即上传）：

| 触发 | 说明 |
|---|---|
| 完成一个可验证的功能 | 功能可用即传 |
| 修完一个 bug | 修复即传 |
| 写了一版文档 | 文档也是产出 |
| 每天收工前 | 至少保证每天一次 |

**上传时必须提供准确的更改描述** —— 不许写"update"，要写清「做了什么、为什么」。

**推送命令**（本机环境特化，详见 `docs/06_ops/RUNBOOK.md`）：

```powershell
$env:HTTP_PROXY=""; $env:HTTPS_PROXY=""; $env:ALL_PROXY=""
$env:http_proxy=""; $env:https_proxy=""; $env:all_proxy=""
git add -A
git commit -F "$env:TEMP\commitmsg.txt"   # 中文提交信息用文件传入，避免乱码
git push origin main
```

> ⚠️ **推送前必须清空代理环境变量**。这是本机的已知坑，
> 端口每次随机变化，不可硬编码规避。

> ⚠️ **另一个已知坑：`git status` 显示 `[origin/main] [gone]`**
>
> 表现：推送明明成功（`EXIT=0`，远程 `ls-remote` 能看到正确的提交），
> 但 `git status` 一直显示 `[gone]`，`git for-each-ref refs/remotes` 输出为空。
> **每推送一次就会复现一次**，属于本机环境的持续性问题，不是操作失误。
>
> 真因（2026-09-18 修订）：**沙箱禁止写入 `.git/refs/remotes/`**，不是缺目录。
> 「建目录 + 写文件」的旧修复方案**已实测证伪，完全无效**。
> `git update-ref` 亦无效（EXIT=0 但零输出、零写入）。
>
> **这不影响推送结果** —— 远程始终是正确的最新提交。只是本地状态显示不准。
> **接受它，不要试图修复。**
>
> ✅ 验收方式（用哈希比对，不用 `[gone]` 判断）：
> ```powershell
> git ls-remote --heads origin main    # 远程哈希
> git rev-parse HEAD                   # 本地哈希 —— 一致即推送成功
> ```
>
> 📌 教训：**`EXIT=0` 不等于成功。** 本环境多处出现「静默丢弃」。
> 📌 完整排查记录见 `~/.workbuddy/skills/hj-git-windows/SKILL.md` 坑 2。

### 2.4 提交信息规范（Conventional Commits）

```
feat:     新功能
fix:      修复 bug
docs:     文档
refactor: 重构（不改变行为）
style:    格式（不影响逻辑）
chore:     杂项（构建、依赖）
perf:     性能优化
test:     测试
```

**正文写清「做了什么、为什么」。**

```
feat: 实现人格档案的冻结层/演化层数据结构

冻结层存储核心性格与说话风格，对话中不可被 AI 修改；
演化层存储对用户的认知与关系状态，每次对话后生成快照。
双层结构的目的是隔离"人格漂移"，只允许演化层发生变化。

详见 docs/02_decisions/D002-核心抽象-人格档案.md
```

### 2.5 必须的配置文件

**`.gitignore`**：

```gitignore
node_modules
dist
build
.DS_Store
*.local
.vite
.env
.env.*
!.env.example
```

**`.gitattributes`**（统一换行符，否则 Windows 上 diff 全是噪音）：

```gitattributes
* text=auto eol=lf

*.png binary
*.jpg binary
*.jpeg binary
*.gif binary
*.ico binary
*.woff binary
*.woff2 binary
```

### 2.6 临时文件不得留在项目目录

**验证脚本、测试数据、临时产物，用完立刻清理。**

清理方式（WorkBuddy 环境的安全机制会拦 Remove-Item）：

```powershell
Move-Item "临时文件" "$env:TEMP\"
```

## 三、文档规范

> 📌 **本节只保留「与文档体系有关、但属于开发纪律」的部分。**
> 完整文档规范（目录归属、命名、frontmatter、6 类模板、生命周期、归档）的
> **唯一出处是 [`../00_meta/DOC_STANDARD.md`](../00_meta/DOC_STANDARD.md)** —— 本节**不复述**，
> 只强调开发者需要记住的三条纪律。
>
> ⚠️ **2026-09-17 修订**：原本节含「单一信息源表」「ADR 格式」两小节，与
> `DOC_STANDARD.md` §四/§六 重复，已删除（这是本项目「单一信息源」原则的自我执行）。

### 3.1 三条文档纪律

| 纪律 | 说明 |
|---|---|
| **改代码必同步文档** | 改了功能 → 改 `01_product/SPEC.md`；推进了阶段 → 改 `00_meta/STATUS.md`。**不要攒着** |
| **发现文档与代码不符 → 改文档** | 文档是描述，代码是事实。代码对了就改文档，不要反过来迁就过期的描述 |
| **新增文档先查 INDEX** | 先看 [`../00_meta/INDEX.md`](../00_meta/INDEX.md) 的信息归属表。**已存在的信息去改那一处，不要新建** |

### 3.2 文档分层（防爆炸的结构性保证）

**核心问题**：文档要么不写，要么越写越多然后全部过期。

**解法：分三层，各司其职。**

| 层 | 文件 | 职责 | 更新频率 |
|---|---|---|---|
| **入口层** | `01_product/PRODUCT.md` / `00_meta/STATUS.md` | 项目全貌 + 当前状态 | **每次阶段推进** |
| **规范层** | `06_ops/DEV_STANDARD.md` / `00_meta/DOC_STANDARD.md` | 协作规则、文档规则 | 很少变 |
| **内容层** | `01_product/SPEC.md` / `PLAN.md` / `02_decisions/` | 需求、计划、决策 | 按需更新 |

**铁律**：

> **任何时刻，新人只读 `01_product/PRODUCT.md` + `00_meta/STATUS.md` 就能知道项目在哪一步。**

> ⚠️ **文档过期不要靠"打标签"解决，要靠"物理隔离"。** 原理与做法见
> [`DOC_STANDARD.md` §7.3](../00_meta/DOC_STANDARD.md) —— 那里解释了为什么只打 `archived` 横幅不够，
> 以及为什么 `_archive/` 目录名本身才是检索器能识别的信号。

## 四、防烂尾机制

### 4.1 里程碑纪律

**每个里程碑必须产出「能跑起来的东西」。**

| ❌ 错误做法 | ✅ 正确做法 |
|---|---|
| Phase 1：设计数据库 → Phase 2：写后端 → Phase 3：写前端 | Phase 1：一个能聊天的完整链路（丑但能跑）→ Phase 2：加记忆 → Phase 3：加可视化 |

**这叫「垂直切片」** —— 每个阶段都贯穿所有层，而不是横着切一层。

**为什么**：横着切的话，你到项目后期才能第一次看到东西跑起来。
而那时候问题最多、最累、最想放弃。

### 4.2 定期演示（硬性要求）

**每两周必须能演示一次。**

| 时间 | 要求 |
|---|---|
| 一周 | 有可见进展（哪怕是丑的） |
| 两周 | **能演示一个完整动作**（比如"从投料到聊上一句"） |

**如果两周演示不出来 → 说明拆得不对，立刻拆细。**

### 4.3 时间盒

**给每个 phase 设时间上限。超时要么砍范围，要么重新评估。**

| 情形 | 处理 |
|---|---|
| 超时 50% 以内 | 继续，但砍掉非核心功能 |
| 超时 100% | **停下来，重新评估方案**，不要硬撑 |

### 4.4 定期审查（每周一次）

**每周花 20 分钟，回答四个问题**：

1. 我现在能说清这个项目每个文件在干什么吗？
2. 有没有文件超过 200 行？
3. 有没有"说不清为什么要存在"的代码？
4. 最近一次提交是什么时候？推送了吗？

**任何一个答案是"否" → 这周先收拾，不加新功能。**

### 4.5 三条红线（触发即停手）

| 红线 | 处理 |
|---|---|
| 🔴 **打开项目感到陌生** | **停止加功能**，花时间读懂现有代码 |
| 🔴 **连续 3 天改不出一个 bug** | 回滚到上一个能跑的版本，重新拆解 |
| 🔴 **两周没有可演示的东西** | 重新评估范围，砍掉一半 |

## 五、AI 协作规范

### 5.1 给 AI 派活的方式

**❌ 不要这样说**：
- "帮我实现一个记忆系统"
- "优化一下代码"
- "加个功能"

**✅ 要这样说**：
- "在这个数据结构下（附上定义），实现一个函数，输入 X 输出 Y"
- "这个函数有 bug：输入 A 时输出 B，期望输出 C，请定位问题"
- "按 `docs/03_specs/memory-schema.md` 里的接口定义实现 `extractFacts`"（⚠️ **文件待建**，见 `docs/00_meta/INDEX.md` 登记项）

**核心**：**AI 需要约束，不是自由。** 你给的约束越具体，产出越可控。

### 5.2 每次让 AI 写代码前，先问自己

1. 我知道这个文件会被放在哪吗？
2. 我知道它的输入输出吗？
3. 如果它写错了，我能看出来吗？

**任何一个答不上来 → 先想清楚再让 AI 动手。**

### 5.3 审查 AI 产出的方法

| 方法 | 说明 |
|---|---|
| **读一遍** | 真的读，不要"看起来差不多就行" |
| **看行数** | 超 200 行要求拆分 |
| **问为什么** | "为什么这里要用 X 而不是 Y？" |
| **跑一遍** | 能跑就跑，看输出对不对 |
| **删一遍** | 挑一段删掉，看会不会坏（不会坏说明是废代码） |

### 5.4 上下文管理

**长对话会导致上下文爆炸。** 处理方式：

- **一个任务一个对话** —— 做完一个功能，开新对话
- **交接靠文档，不靠对话历史** —— 这就是 `01_product/PRODUCT.md` + `00_meta/STATUS.md` 存在的意义
- **把决策写进文档** —— 否则新对话里的 AI 会重新问你一遍，或者更糟，推翻你的决策

**本项目专用交接话术**（复制给新对话的 AI）：

```
请先读 docs/01_product/PRODUCT.md 了解项目全貌，
再读 docs/00_meta/STATUS.md 了解当前进度，然后读
docs/06_ops/DEV_STANDARD.md 了解协作规范。
不要推翻 docs/02_decisions/ 里的已定决策，
除非你能说明为什么应该改。
```

## 六、技术选型规范

### 6.1 Boring Technology 原则

**优先选无聊、成熟、文档多的技术。**

| 判断维度 | 加分 |
|---|---|
| 存在 5 年以上 | ✅ |
| 官方文档完整（最好有中文） | ✅ |
| 大量真实项目在用 | ✅ |
| 出问题时能搜到答案 | ✅ |
| 你熟悉 | ✅✅✅ |

**新技术的额度：一个项目一样**（见原则 2）。

### 6.2 依赖引入的判断

引入任何依赖前问三个问题：

1. **它省下的工作量 > 学习成本吗？**
2. **它死掉了（停止维护）我怎么办？**
3. **它会不会成为我理解不了的黑盒？**

**警惕**：为了省 100 行代码，引入一个需要学 2 天的库 —— 这笔账通常是亏的。

### 6.3 优先「零后端」

**后端是复杂度黑洞。** 能纯前端就纯前端。

需要后端时，**让它尽可能薄** —— 只做三件事：代理请求、读文件、写文件。

**判断标准**：如果这个后端删掉，前端退化成一个更简单的版本但仍能跑，
那它就是一个好的后端。

### 6.4 前端视觉取值：只认 `DESIGN_STANDARD.md`

**UI 代码里不允许出现规范之外的色值、圆角、阴影。**

| 要做的事 | 去哪 |
|---|---|
| 查色值 / 圆角 / 阴影 / 动效参数 | `DESIGN_STANDARD.md` §一（**唯一信息源**） |
| 查哪些 class 禁止用 | `DESIGN_STANDARD.md` §三（可执行正则） |
| 提交前自查 | `DESIGN_STANDARD.md` §六 |
| 想知道为什么定这套 | `02_decisions/D008-UI方案与视觉规范.md` |

> ⚠️ **不要在本文件或代码注释里复制一份色板。** 那会造成两处不一致 —— 违反规则 2（单一信息源）。

## 七、本项目特化条款

### 7.1 强制项

| 条款 | 说明 |
|---|---|
| **及时上传 GitHub** | 见 2.3，完成即传，附准确描述 |
