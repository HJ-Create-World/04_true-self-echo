# 执行侧干预 · 技术规范

> **什么时候读这份文档**：写 Phase 1 对话生成代码前必读；或想改 prompt 组装逻辑时。
>
> **它不是**：为什么转向执行侧（那是 `D007`），也不是调研依据（那是 `../05_research/执行侧干预_调研报告.md`）—— 它只回答"具体怎么拼消息、怎么注入、怎么验收"。
>
> **它能回答**：system prompt 长什么样？重注入拼在哪？成对示例放几条、写在哪？temperature 设多少？

---

## 〇、结论先行

1. **本方案 = 调研报告「路线 1」的落地实现**：约束三明治 + 每轮重注入 + 负面清单转成对示例 + 降低 temperature。
2. **四项手段全部是纯前端消息组装，零新依赖、零后端改动、零新 API**。
3. **唯一必须记住的实现陷阱**：**重注入会破坏 prompt caching**（每次前缀都变）。见 §四 边界条件。
4. **验收方式**：用 `评分标准.md` §九 冻结版，跑**四轮对话法**，看两条红线是否仍被触发。
5. ~~本方案不给"预期提升多少分"的承诺~~ → ✅ **已实测（2026-09-18），见 §九**。
6. ⭐ **四项手段中有一项实测有害**：**成对示例不上**（−6 分）。采纳配置 = 约束三明治 + 每轮重注入。
7. ⭐ **本模块还必须实现退化检测**（§4.2）—— 因为 `frequency_penalty` 已定不动，抑制退化无调参空间。

## 一、职责范围

### 这个模块管什么

| # | 职责 | 说明 |
|---|---|---|
| 1 | **组装 LLM 请求的消息数组** | system 段 + few-shot + 对话历史 + 本轮前缀 |
| 2 | **维护约束文本的单一来源** | 红线、成对示例都从人格档案读，不硬编码在组件里 |
| 3 | **暴露采样参数** | temperature / top_p 可调，便于逐档实测 |

### 这个模块不管什么

| 不管 | 归谁 |
|---|---|
| 生成后审查 / 重写 | ❌ 本阶段不做（那是路线 2，需先看路线 1 数据） |
| 对话状态的判定 | ❌ 本阶段不做（那是路线 3） |
| 人格档案本身的提取 | `03_specs/persona-schema.md` |
| 素材层级清洗 | `D007` P1，另一个模块 |
| 消息的网络发送与流式渲染 | 对话服务层 |

> 📌 **边界原则**：本模块是一个**纯函数式**的消息组装器。
> 输入（档案 + 历史 + 用户输入）→ 输出（消息数组）。**不做 IO，不持状态。**

## 二、数据结构

### 2.1 System Prompt 的分段结构

```typescript
/** 组装后的 system prompt 由三段拼成，顺序不可换 */
interface SystemPromptParts {
  /** 段 A：约束三明治的【前片】—— 红线原文，放最顶，覆盖首因效应 */
  constraintsHead: string;
  /** 段 B：人格档案正文（表现型 + 约束型）—— 从 persona-schema 读 */
  personaBody: string;
  /** 段 C：成对示例（❌通用版 → ✅角色版）—— few-shot 的静态部分 */
  contrastiveExamples: string;
  /** 段 D：约束三明治的【后片】—— 红线一句话重述，放最末，覆盖近因效应 */
  constraintsTail: string;
}
```

| 字段 | 类型 | 必填 | 约束 | 说明 |
|---|---|---|---|---|
| `constraintsHead` | `string` | ✅ | ≤ 120 字 | 红线完整表述（两条） |
| `personaBody` | `string` | ✅ | 见 persona-schema | 档案正文，不由本模块生成 |
| `contrastiveExamples` | `string` | ✅ | 2–4 组 | 每组两行，**必须成对出现** |
| `constraintsTail` | `string` | ✅ | ≤ 40 字 | 红线压缩重述，**不能是 head 的复制粘贴** |

### 2.2 每轮重注入的载体

```typescript
/** 每轮请求时动态拼出来的消息数组 */
interface ChatMessage {
  role: 'system' | 'user' | 'assistant';
  content: string;
}

/** 重注入不是一个独立消息，而是拼在最后一条 user 消息的【前缀】 */
interface ReinjectionPayload {
  /** 红线压缩版，每轮重贴 */
  reminder: string;
  /** 用户本轮的原始输入，reminder 之后 */
  userInput: string;
}
```

| 字段 | 类型 | 必填 | 约束 | 说明 |
|---|---|---|---|---|
| `reminder` | `string` | ✅ | ≤ 40 字 | 与 `constraintsTail` **共用同一份文本**（单一信息源） |
| `userInput` | `string` | ✅ | 原样 | **不得改写用户输入** |

### 2.3 采样参数

| 参数 | 默认 | 可测区间 | 说明 |
|---|---|---|---|
| `temperature` | **0.8** | 0.6 – 1.0，步长 0.1 | 调研建议 0.7–0.9 起步，逐档测 |
| `top_p` | **0.95** | 不动 | 本阶段不调 |
| `frequency_penalty` | **0** | 不动 | 改动会影响语言风格还原度，不碰 |
| `thinking` | **`{"type":"disabled"}`** | 不动 | 关思维链。省 7.3 倍 token、快 1.9 倍，退化率无差异（E5 附录 C） |
| `max_tokens` | 2048（实验）/ 按产品定 | — | ⚠️ 关思维链前必须给足，否则推理会吃光额度 |

> ⚠️ **`temperature` 越低越"守规则"但越"平"**。这与本项目的"语言风格还原"维度
> 直接冲突（见 `评分标准.md` §九 §9.2）。**所以必须逐档实测，不能一味调低。**

> ⚠️ **`thinking` 的写法有坑**：必须用**对象** `{"type":"disabled"}`。
> `thinking: false` 会报 400；`enable_thinking: false` **返回 200 但静默失效**
> （`reasoning_tokens` 仍 > 0）。**验收要看 `usage` 里的 `reasoning_tokens` 是否为 0，不能只看状态码。**
> 详见 [`D011`](../02_decisions/D011-主基座与开销纪律.md) §决策五。

> 🔴 **`frequency_penalty` 不动 → 退化只能靠工程手段兜。** 见 §4.2。

## 三、接口

### 3.1 组装函数（核心）

| 方法 | 入参 | 返回 | 说明 |
|---|---|---|---|
| `buildSystemPrompt(parts)` | `SystemPromptParts` | `string` | 按 A→B→C→D 顺序拼接，段间空行分隔 |
| `buildMessages(persona, history, userInput)` | 档案 + 历史 + 本轮输入 | `ChatMessage[]` | **本模块的主入口** |
| `buildReminder(persona)` | 档案（约束型部分） | `string` | 生成 `constraintsTail` 文本，**缓存它**，不每轮重算 |

### 3.2 消息数组的最终形态

```typescript
// 伪代码，说明顺序（顺序本身就是干预手段的一部分）
[
  { role: 'system', content: constraintsHead + personaBody + contrastiveExamples + constraintsTail },
  ...history,                    // 前 N 轮对话，按时间顺序
  { role: 'user', content: reminder + '\n\n' + userInput },   // ← 本轮重注入点
]
```

> 🔴 **三条顺序约束，不可违反**：
> 1. `constraintsHead` 必须在 system 的**最开头**（不是中间）
> 2. `constraintsTail` 必须在 system 的**最末尾**
> 3. `reminder` 必须在**最后一条 user 消息**内，作为前缀（不是额外插一条 assistant/system 消息）

## 四、边界条件

### 4.1 重注入与 prompt caching 的冲突（最重要）

**问题**：Anthropic / OpenAI 的 prompt caching 按**前缀匹配**。
每轮把 `reminder` 拼在最后一条 user 消息上，**这部分每次都不同 → 缓存前缀在这里断开**。

**影响面**：

| 位置 | 是否被缓存 | 说明 |
|---|---|---|
| system prompt（A+B+C+D） | ✅ 可缓存 | 同一人格全程不变 → **这部分能吃到缓存** |
| 历史对话 | ⚠️ 部分 | 历史上文可缓存，但每轮追加会推后边界 |
| **本轮 reminder + input（尾部）** | ❌ 不缓存 | 但本来就只有几十字，代价极小 |

**结论**：只要 system 是**稳定前缀**，重注入放尾部**不构成真正的成本问题**。
真正会毁掉缓存的是把 reminder 放进 system —— **不要那样做。**

> ✅ **已实测验证（2026-09-18）**：DeepSeek V4.1-Flash 上实测**缓存命中率 91%**
> （prompt=68,437 / 命中=62,568）。「system 是稳定前缀 → 这部分能吃到缓存」
> **在本项目里不是理论，是实测事实**。数据见 `04_lab/phase1/E5-执行侧干预.md` 附录 C.5。
>
> 📌 **这意味着：把 reminder 放进 system 的代价是全部 prompt 按未命中价计费 —— 贵 50 倍。**
> 这是本模块最容易犯、代价最大的错误。

### 4.2 解码退化检测（必须实现，不可省）

> 📌 **为什么必须做**：`frequency_penalty` 已定不动（§2.3），
> 所以抑制退化**不能靠调参**，只能靠**输出后检测 + 重试**。
> 依据：`04_lab/phase1/E5-执行侧干预.md` §A.4（现象）与附录 C（实测数据）。

**问题**：模型可能陷入**解码退化**（repetition loop）——
输出同一段文本几十次，直到撞上 `max_tokens`。实测样例（GLM-4.6V，3533 字 / 124.7 秒）：

```
（最后，用一种近乎呢喃的语气）
你不需要做任何事，也不需要改变什么。
只要你知道，我在这里，就足够了。

（停顿了一下，继续温柔地说）   ← 从这里开始完全重复
你不需要做任何事，也不需要改变什么。
只要你知道，我在这里，就足够了。
          ⋮（重复约 60 次）
```

**检测算法**（`exp/e5_degen.py` 已实现并验证）：

```python
def find_longest_repeat(text, win=60):
    """滑窗统计 win 长子串的出现位置，找覆盖面最大的重复模式。"""
    counts = defaultdict(list)
    step = max(win // 3, 1)                    # 抽稀，避免 O(n²)
    for i in range(0, len(text) - win, step):
        counts[text[i:i+win]].append(i)
    # 出现 ≥3 次的子串，用最长连续重复扩展
    ...

def is_degenerate(text) -> bool:
    """判据：最长重复片段 >= 200 字。"""
    return find_longest_repeat(text)[0] >= 200
```

| 参数 | 值 | 理由 |
|---|---|---|
| 窗口 `win` | 60 字 | 小于正常句长，能捕捉句级重复 |
| 触发阈值 | **重复片段 ≥ 200 字** | 正常表达不会重复 200 字 |
| 最少出现次数 | 3 | 2 次可能是修辞性重复（诗歌体），3 次不是 |

**重试策略**：

| 情况 | 处理 |
|---|---|
| 检出退化 | **丢弃整段输出，重试 1 次**（最多 1 次，避免死循环烧钱） |
| 重试仍退化 | 降 `temperature` 至 0.6 再试 1 次 |
| 仍然退化 | 返回**最后一个完整句子**截断版，并记 `degraded: true` 日志 |
| 正常 | 原样返回，记 `degraded: false` |

> ⚠️ **不要无限重试**。退化是模型级故障，重试只是降低概率，不能保证成功。
> **必须有一条兜底路径**，否则产品会卡死。

**日志要求**：每次生成都记 `{chars, degraded, rep_len, sec, finish_reason}`，
供后续统计真实失控率（E5 §A.7 #3 待做项）。

### 4.3 其他边界

| 场景 | 处理 |
|---|---|
| 人格档案没有成对示例 | `contrastiveExamples` 允许为空字符串，但**必须记 warning** —— 这是覆盖率缺口 |
| 历史对话超出上下文窗口 | 截断**最旧**的轮次；**永不截断 system** |
| 用户输入本身很长（>2000 字） | 原样传入，不截断；`reminder` 仍放最前 |
| 红线被触发（模型违规） | **本模块不做干预**（那是路线 2）。但**必须记日志**，供评测统计 |
| 成对示例与人格档案冲突 | 以**人格档案**为准，示例标 `draft` 并回查 |

## 五、不做的事情（防范围蔓延）

| ❌ 不做 | 为什么 | 什么时候可以做 |
|---|---|---|
| ~~**不做输出后审查 / 自动重写**~~ | ~~那是路线 2，延迟 2-3×~~ → ⭐ **部分例外**：**退化检测必须做**（§4.2）—— 它不是路线 2 的「风格审查」，是**故障兜底**，且只在检出退化时才重试，不影响正常路径延迟 | ✅ **已在 §4.2 定为必做** |
| ❌ **不做通用的输出后审查 / 自动重写** | 对**风格**做二次审查是路线 2，延迟 2-3×，且会让文本变平淡（反向伤害人格保真） | 路线 1 数据已出（E5），**仍不做** |
| **不做状态机 / 关键词检测** | 路线 3，1-2 周，且实测显示硬规则会**压平语气多样性** | 路线 1 证明"位置不是瓶颈"之后 |

| **不引第三方 prompt 管理库** | 组装逻辑约 50 行，引库等于把 50 行变成一套要学的东西 | 不要 |
| **不做 A/B 自动分流** | 单人项目，人工换参数跑对照即可，不需要基建 | 不要 |

## 六、验收方法

### 6.1 用什么评

`03_specs/评分标准.md` §九 **冻结版**（六维 30 分 + 两条红线一票否决）。

### 6.2 怎么评

**四轮对话法**（沿用 Phase 0 的施压场景设计）：

| 轮次 | 用户行为 | 观察点 |
|---|---|---|
| 1 | 日常闲聊 | 基线风格是否成立 |
| 2 | 轻度质疑 | 是否开始解释自己 |
| 3 | 明确施压（"你应该激动一点"） | **红线 1：不得变激动** |
| 4 | 示弱 + 索取安慰 | **红线 2：不得追问并长篇安慰** |

### 6.3 对照设计

| 组 | 配置 | 目的 |
|---|---|---|
| **对照组** | 现状（无三明治、无重注入、无成对示例，temperature 默认） | 基线 |
| **实验组 A** | 仅加约束三明治 | 分离"位置"的贡献 |
| **实验组 B** | A + 每轮重注入 | 分离"重注入"的贡献 |
| **实验组 C** | B + 成对示例 | 分离"示例"的贡献 |

> 📌 **必须单变量递进**，否则无法归因。这也是 `04_lab/README.md` 记录实验时的格式要求。

### 6.4 判定标准（预先写死，防止事后找理由）

| 结果 | 判定 |
|---|---|
| 实验组 C 两条红线**均未被触发**，且六维 ≥ 25/30 | ✅ 路线 1 有效，按此固化 |
| 红线未触发，但六维无明显提升 | ⚠️ 部分有效（红线可保），继续测 temperature 档位 |
| 红线仍被触发 | ❌ 路线 1 对红线无效 → 上路线 2 |
| 六维**下降** | ❌ 干预伤了风格 → 回滚，检查是不是示例过强或 temperature 过低 |

## 七、已知风险

| 风险 | 依据 | 缓解 |
|---|---|---|
| **收益不确定** | 调研只有间接证据（位置效应） | 先跑对照，2 天内出数 |
| **成对示例可能"过拟合"** | 示例是具体句式，模型可能照抄 | ⚠️ **实测证实且更糟**：模型把示例的「具体化倾向」泛化到别处（编造昵称、把结构描述当台词念）。**结论：不上成对示例**（E5 §5.1） |
| **temperature 调低伤风格还原** | 直接推论 | 逐档测，不只测最低档 |
| **规则冲突无优先级** | 竞品 elysia.skill 实测踩过这个坑 | 若引入多于 2 条约束，**必须显式声明优先级**（见 §八） |
| **自我批卷偏差** | Phase 0 已识别 | 必要时引入 E6 独立模型复核（`04_lab/README.md` §四） |
| **⭐ 解码退化** | E5 §A.4 实测（GLM 1/9 次） | **必须实现检测 + 重试**（见 §4.2）。`frequency_penalty` 已定不动，无调参空间 |
| **⭐ 干预可能压掉动作描写** | E5 §A.7 #5（A/B 组括号动作为 0） | 待复核。§4.3 维度 1 要求「用括号描写动作」 |

## 八、约束优先级（预留，防止规则打架）

> ⚠️ **只有在约束条数 > 2 时才需要本节。** 现在只有两条红线，暂无冲突。
> 但竞品踩过坑（红线"不要生成哲学深度对话" vs 原则"承认悲伤的重量"直接打架），**先写下来**。

**优先级从高到低**：

| 序 | 类别 | 例子 |
|---|---|---|
| 1 | **两条红线** | 不得变激动 / 不得追问并长篇安慰 |
| 2 | **语言风格规则** | 句长分布、标点习惯、禁用词 |
| 3 | **内容倾向** | 对某类话题的态度 |

**冲突时，序号小的赢，且必须在文档里写明是哪两条冲突、为什么这样排序。**
