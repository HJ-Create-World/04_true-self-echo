# D008 · UI 方案与视觉规范

> **什么时候读这份文档**：想换掉 Tailwind、想改成暗色模式、或觉得"水彩风太重了想简化"时。
>
> **它不是**：具体色值和 class 的清单（那是 `../06_ops/DESIGN_STANDARD.md`）—— 它只回答"为什么用这套"。
>
> **它能回答**：为什么最后用了 Tailwind？为什么放弃了调研时更推荐的 Reka UI / Naive UI？这个决策最脆弱的环节在哪？

- **状态**：已采纳
- **日期**：2026-09-16
- **决策者**：HJ
- **取代**：本决策**部分推翻** `../05_research/前端风格与UI库选型.md` 中「不推荐 Tailwind」的结论

---

## 背景

`D003` 把「UI 库」一栏留成了「**允许引入**（具体待定）」，理由是"风格未定，需要预留可调整空间"。
随后 `../05_research/前端风格与UI库选型.md` 做了一轮调研，**当时的结论是：不推荐 Tailwind**，推荐 Reka UI + 自研样式。

那个结论的推理链是：

> Tailwind 会把"改样式"变成"学一套新 DSL"，
> 违反 `DEV_STANDARD.md` 原则 2「一个项目只学一样新东西」——
> 本项目的新东西额度应该留给人格建模，不该花在 CSS 工具链上。

**这个推理本身没错。但它建立在一个当时未知的前提上。**

2026-09-16，HJ 确定了视觉风格：stylekit.top 的 **watercolor-style 模板**。该规范交付给我们的形式是
**一整套 Tailwind class 词典** —— `rounded-2xl md:rounded-3xl`、`bg-[#faf8f5]`、
`shadow-[0_4px_20px_rgba(74,111,165,0.12)]`、`duration-500`、`active:scale-[0.98]`、
甚至连**禁止项都是用 Tailwind 正则写的**（`^rounded-none$`、`^font-(?:black|bold)$`）。

**前提变了，结论就得重算。** 这是本决策的全部由来。

---

## 选项

| 选项 | 描述 | 后果评估 |
|---|---|---|
| A · Tailwind CSS v4 + 语义变量 | 直接消费模板给的 class 词典；变量集中于 `@theme` | ✅ 规范可**逐字照抄**，零翻译损耗<br>✅ 禁止项正则可直接接 lint<br>❌ 引入新 DSL（原调研的核心反对理由） |
| B · Reka UI + 自研 CSS | 调研原推荐：无样式组件 + 自己写 CSS | ❌ 需把**每一个** Tailwind class 手工翻译成原生 CSS<br>❌ 模板规范里的禁止项正则全部失效，失去自动校验<br>❌ 翻译过程会**必然漂移**（"这个 4px 还是 6px 来着"）<br>✅ 不引入新 DSL |
| C · Naive UI（或同类成品库） | 直接拿现成组件 | ❌ 组件自带视觉语言，与水彩风**正面冲突**，要覆盖的样式比重写还多<br>❌ 水彩风的核心是"纸感"，成品库没有这个概念 |
| D · 不用任何 CSS 方案，纯手写原子类 | 每个元素手写 style | ❌ 等于 B 的劣化版，还丢了缓存与协作能力 |
| E · shadcn-vue + 覆盖主题 | 组件源码进项目，主题用 CSS 变量 | ⚠️ 比 C 好（源码可控），但默认视觉仍是"现代 SaaS"，覆盖量大<br>⚠️ 与 A 不互斥，**可作为 A 的后续增补** |

### 为什么不用 Reka UI（调研原推荐，需要正面回答）

Reka UI 本身没问题 —— 它仍是**无样式 headless 组件**的最优解。
问题在于**它与 Tailwind 不是竞争关系，而是互补关系**：

> Reka UI 解决「组件行为」（弹窗怎么关、焦点怎么走），
> Tailwind 解决「视觉取值」。
> **模板规范只涉及后者。**

所以真正的选项不是「Reka UI 还是 Tailwind」，而是
**「Tailwind 还是手写 CSS」** —— 而手写 CSS 要把一份现成的 class 词典人工翻译一遍。

### 为什么不用 Naive UI（调研备选，需要正面回答）

调研把它列为 §3.2 备选。**排除理由是视觉层不可控**：
Naive UI 的组件带着一整套自己的设计语言（默认圆角 4px、灰阶系统、Material 味阴影）。
水彩风格恰好在**每一个维度上都与它相反**（大圆角 vs 小圆角、弥散阴影 vs 线性阴影、衬线 vs 无衬线）。
把它改造成水彩风的成本，高于直接用 Tailwind 写一套组件。

> ⚠️ **但 B 和 C 也没有全废**：如果后续需要复杂交互组件（日期选择、树形、可拖拽排序），
> **优先引入 Reka UI 作行为层**，视觉层仍由我们自己的 Tailwind class 控制。
> 决策 A 并不排斥 Reka UI —— 它俩本来就是两层。

---

## 决定

**采纳 A：Tailwind CSS v4 + 语义化 CSS 变量，视觉规范集中在 `06_ops/DESIGN_STANDARD.md`。**

三条附带约束：

| # | 约束 | 为什么 |
|---|---|---|
| 1 | **所有色值/圆角/阴影只在 `@theme` 定义一次**，代码里禁止魔法值 | 换主题时只改一处（承接 `D003` 的「CSS 变量驱动主题层」） |
| 2 | **禁止项正则接进 lint** | 规范里已经写好了 5 条正则，不用白不用 |
| 3 | **组件行为层随时可引入 Reka UI**，但**不引任何自带视觉的组件库** | 保住"纸感"这个单一视觉源 |

## 后果

**正面**

- 模板规范**可逐字消费** —— 从规范到代码零翻译损耗，这是最大收益
- 禁止项**可自动校验**（5 条正则可直接用于 lint / review 脚本），规范不会因为"人忘了"而失效
- 水彩风格高度可复制：所有页面共享同一套 token，新页面不会长歪
- Tailwind 是**强约束型**工具：class 写不多，天然抑制"这个组件再加点样式"式的范围蔓延
- 与 `D003` 的「CSS 变量驱动主题层」一致，不是推翻架构

**负面 / 代价**（诚实部分）

- ⚠️ **本决策推翻了我（AI）上一轮调研报告的核心结论。** 根因不是推理错，而是
  **调研时不知道风格规范会以 Tailwind 语法交付**。这个新的信息出现后，原来的"不引入新 DSL"
  从一个**成本**，变成了**避免手工翻译**的手段 —— 成本项反转成了收益项。
  原来的结论已经按 `DOC_STANDARD.md` 规则修正（见 `../05_research/前端风格与UI库选型.md` §〇 修订说明）。
- ⚠️ **确实引入了 Tailwind 这个新东西**，与 `DEV_STANDARD.md` 原则 2「一个项目只学一样新东西」
  **存在张力**。缓解判断见下方维护点 —— 我认为这个额度花得值，因为它换回了「规范可自动校验」。
- ⚠️ **绑定了 Tailwind 生态**。要换回手写 CSS，需重写全部视觉层。缓解：所有取值走 CSS 变量，
  换的不是"值"而是"消费方式"。
- 模板里有部分写法偏重（如 `md:rounded-3xl`），需要在移动端实测挤压情况

**后续维护点 / 缓解措施**

| 风险 | 缓解 |
|---|---|
| 违背「只学一样新东西」 | 判定：**Tailwind 的边际学习成本已被规范消化** —— 我们不需要"学一套 DSL 再设计风格"，而是"照抄给定的 class"。真正要动脑的部分（选哪个色、几档圆角）规范已经决定了。**人格建模仍是本项目唯一的新知识投入方向。** |
| 规范漂移（写出规范外的值） | `DESIGN_STANDARD.md` §一 声明为取值的唯一信息源，§三 给可执行正则 |
| Tailwind 版本升级破坏写法 | 锁大版本；升级前先跑一遍 §六 自检清单 |
| 水彩风在数据密集页（评测结果表）不可读 | **触发条件**：若评分表/日志页出现可读性问题，允许该页**局部**采用更紧凑的排版（仍遵守色彩与圆角约束）。这需要修改本 ADR 或新增一份，不能悄悄改 |

## 这个决策什么情况下会失效

写下来，方便以后判断是否该推翻它：

1. **Tailwind 的 class 词典覆盖不了某个交互**（如复杂动画编排）→ 局部用原生 CSS，但仅限该处并注明原因
2. **水彩风在真实使用中显得廉价或碍事**（比如用户反馈"看不清"）→ 重新评估，可能需要降级为"水彩点缀 + 中性主体"
3. **Phase 1 完成后发现视觉维护成本 > 收益** → 此时应重新做一轮调研，而非继续打补丁
