## 背景

### 促成这次决策的三个事实

**事实一：本地算力被证伪。**
原计划用 `qwen3.6:latest`（22.29GB）本地复验，HJ 实测后叫停 ——「这台本地笔记本带不动」。
`D005` 说「效果上限受底座模型能力限制」，本地小模型的测试已经显示这是真的
（`deepseek-r1:latest` 4.87GB 的 control 组只有 9/30）。

**事实二：`D007` 已预判要重测。**
`D007`「什么情况下要重审」第三条原文：

> **换了更强的模型** → RLHF 顺从本能可能不同，需重新测

**所以在 DeepSeek 上复验 E5 不是额外开销，是决策链上已排好的一步。**

**事实三：HJ 提出了三个真实的顾虑。**

> ① 开发过程中请控制使用，避免开销过多
> ② 如果每次更换模型都要做大量的适配和测试，对我的钱包的消耗是不是也比较大
> ③ deepseekV4.1-Flash 的能力能不能胜任这个项目，作为生成能力的开发基座

**本决策要逐条回答这三个问题。**

## 决策一：主基座选 DeepSeek V4.1-Flash

### 选项

| 选项 | 描述 | 后果评估 |
|---|---|---|
| **A · DeepSeek V4.1-Flash** | 1M 上下文；缓存命中价 = 未命中的 1/50；OpenAI + Anthropic 双兼容 | ✅ 实测 48 次请求 0 退化 0 失败<br>✅ 缓存命中率实测 **91%**<br>✅ 就是 Phase 0 计划要接的模型，迁移成本 0 |
| B · GLM-4.6V | 已有 6000 万 token 免费额度 | ⚠️ 实测出现 3533 字死循环（1/9）<br>⚠️ R4 字数波动 68–3533，稳定性差<br>❌ 免费额度是**有限资源**，不适合当长期基座 |
| C · 本地 Ollama | 零成本、零合规风险 | ❌ 笔记本带不动（已实证）<br>❌ 质量不足（9/30） |
| D · 暂不定，继续测 | 保持现状 | ❌ 正式数据生产需要确定的基座，拖下去阻塞 Phase 1 |

### 为什么是 A

**四条理由，按分量排序：**

| # | 理由 | 依据 |
|---|---|---|
| 1 | ⭐ **缓存命中价差 50 倍，而本项目恰好是缓存友好型** | `execution-control.md` §4.1 论证「system 是稳定前缀」→ 附录 C.5 **实测命中率 91%** |
| 2 | ⭐ **稳定性实测优于 GLM** | GLM 1/9 次死循环（3533 字）；DeepSeek **0/16 次**，最长 168 字 |
| 3 | **1M 上下文** | 人格档案 + 技能包 + 长对话历史塞得下，不用做复杂裁剪 |
| 4 | **迁移成本为 0** | 就是 Phase 0 计划要接的模型（`PLAN.md`） |

> 📌 **第 1 条不是「单价便宜」，是「结构性优势」。**
> 本项目每轮都要带一份 3000+ 字的人格档案，如果按未命中价算，成本会高 50 倍。
> **缓存命中率直接决定了这个项目的经济性。**

### ⚠️ 四个必须知道的坑

| # | 坑 | 说明 |
|---|---|---|
| 1 | **峰谷定价** | peak = 北京时间 09:00–12:00、14:00–18:00（周一至五），是谷时的 **2 倍**。批量实验避开 |
| 2 | **模型 ID 已变** | `deepseek-chat` / `deepseek-reasoner` 于 2026-07-24 退役。当前只有 `deepseek-flash` 与 `deepseek-v4-pro` |
| 3 | **数据合规** ⚠️ | 投料素材会上传第三方。**若做真人素材（朋友/亲人聊天记录），涉及他人个人信息** —— 与 `SPEC.md` §十二 直接相关 |
| 4 | **可用性波动** | 高峰期可能 Server Busy，需 fallback —— 这正是「多后端可切换」的价值 |

> ⚠️ **第 3 条是最需要警惕的。** 二次元角色的素材是公开素材，上传无妨；
> 但**真人模仿场景的素材是他人隐私**。这条不能靠「我们会注意」解决，
> **必须有机制**：真人素材默认走本地 Ollama，或在产品层做显式的上传确认。
> 归属：`SPEC.md` §12.4 上线前清单 + 待决项 #8（合规专项调研）。

## 决策二：回答「换模型要花多少钱」（HJ 的问题 ②）

### 结论：**在这个架构下，换模型的成本几乎为零。**

**不是设计承诺，是既成事实。** `exp/e5_runner.py` 的三个后端
（glm / deepseek / ollama）**共用同一套调用代码**，因为都走 OpenAI 兼容协议：

```python
def get_provider(name: str, env: dict) -> dict:
    key = name.upper()
    return {
        "base_url": env.get(f"{key}_BASE_URL"),   # ← 只差这三行
        "api_key":  env.get(f"{key}_API_KEY"),
        "model":    env.get(f"{key}_MODEL"),
    }
```

| 换模型时要改什么 | 实际情况 |
|---|---|
| 调用代码 | **零改动** |
| 请求参数格式 | **零改动**（同一份 `payload`） |
| 返回解析 | **零改动** |
| **要改的** | **`.env` 里 3 行** |

**这不是巧合，是 `PLAN.md` §Phase 1 的隐藏重点 1 已定好的设计：**

> 模型接入层要同时支持本地 Ollama 和云端 OpenAI 兼容 API，**用一个配置文件切换**

### 换模型要花的钱 = 一次复验 ≈ ¥0.05

| 类型 | 成本 | 说明 |
|---|---|---|
| 接口连通性测试 | ≈ 0 | 一次单轮调用，几厘以下 |
| **效果复验（四组 × 3 次 = 48 次请求）** | **≈ ¥0.05** | 实测值，含缓存命中 |

> **量级判断**：换一次模型的复验成本约等于**一瓶矿泉水的 1/40**。
> **这个问题不需要做任何架构性焦虑。**

## 决策三：回答「DeepSeek 能不能胜任」（HJ 的问题 ③）

### 结论：**能，且在候选里是最合理的那个。**

分两层看，因为「胜任」在你的项目里有两个含义。

### 第一层：作为「生成能力基座」——能胜任

| 论据 | 出处 | 实测/推断 |
|---|---|---|
| 强模型基线就守得住两条红线 | E5 附录 B.5 | ✅ **实测**：四组全部通过 |
| control 组直接拿 17/30（vs 小模型 9/30） | E5 §4.2b | ✅ **实测** |
| 配置 B 拿到 **23/30**，逼近闭环线 24 | E5 §5.5 | ✅ **实测** |
| 0 退化 / 0 失败（48 次请求） | E5 附录 B.3 | ✅ **实测** |
| 91% 缓存命中率 | E5 附录 C.5 | ✅ **实测** |

### 第二层：作为「唯一基座」——**不建议**

这里有个**必须说清楚的坑**：**不同模型的失效模式不一样。**

| 模型 | 它的特定失效 |
|---|---|
| `deepseek-r1:latest`（弱） | 自居「虚拟歌姬 / 系统小助理」；顺从本能过强 |
| `glm-4.6v` | **解码退化**（3533 字死循环，1/9 次） |
| `deepseek-flash` | 「54.8kg」被当口癖反复自嘲（轻微） |

**E5 的跨模型对比给出的核心结论是：**

> **换模型带来的差异 > 消息组装手段带来的差异。**

**反过来读就是**：不同模型需要不同的干预配方。**「唯一基座」意味着放弃对照能力。**

### ✅ 采纳的分工

| 角色 | 模型 | 理由 |
|---|---|---|
| **主基座（跑正式数据）** | **DeepSeek V4.1-Flash** | 1M 上下文 + 缓存便宜 + 基线稳 |
| **调 prompt（免费验证层）** | **GLM-4.6V** | 6000 万免费额度；**调 prompt 是最烧 token 的阶段** |
| **隐私兜底** | **Ollama 本地** | 真人素材喂它，不触网 |
| 候选/对照 | 未来再评估 | **不急着扩** |

## 决策四：开销纪律（HJ 的问题 ①）

### 三条硬纪律

| # | 纪律 | 省在哪 | 怎么执行 |
|---|---|---|---|
| 1 | **调 prompt 阶段一律用 GLM-4.6V** | 调 prompt 是最烧 token 的阶段，**这段完全不花钱** | 改 `.env` 的 `DEFAULT_PROVIDER=glm` |
| 2 | **避开峰时** —— 北京时间 周一至五 09:00–12:00、14:00–18:00 是 2 倍价 | **直接砍半** | 批量实验排在晚间或周末 |
| 3 | **`repeat` 按需** —— 默认跑 1 次，只在需要测稳定性/退化率时才放大 | 避免无意义的重复采样 | `python e5_runner.py deepseek "" 3` |

### 单次开销量级（给你个锚）

| 动作 | 花费 |
|---|---|
| 一次连通测试 | ≈ ¥0.000x |
| 一次完整 E5 四组实验（48 次请求） | ≈ **¥0.05** |
| 十次复验 | ≈ ¥0.5 |

> **这个量级下，「省钱」不是主要风险。真正会烧钱的是失控** ——
> 忘记改 `repeat` 跑出几百次、循环调用、跑错模型。
> **所以纪律要落成硬约定，比事后心疼有用。**

### 结构性省钱：缓存

**本项目 91% 的 prompt 会命中缓存**，因为 `execution-control.md` 的两条顺序约束
保证了 system 是稳定前缀：

| 方案 | 缓存 | 代价 |
|---|---|---|
| constraintsHead 放 system 开头 + constraintsTail 放 system 末尾（**当前方案**） | ✅ **保住** | 无 |
| 把 reminder 放进 system | ❌ **毁掉缓存** | 每轮全量重算 |

> ⚠️ **这是最容易犯的错。** 把每轮变的 reminder 塞进 system 看起来「更强调」，
> 实际会让**所有轮次都按未命中价计费 —— 贵 50 倍。**
> **已固化在 `execution-control.md` §4.1，不要改。**

## 决策五：关思维链

**正式实验统一 `thinking:{"type":"disabled"}`。**

| 指标 | thinking on | thinking off | 改善 |
|---|---|---|---|
| completion tokens | 9,346 | **1,273** | **省 7.3 倍** |
| R4 均耗时 | 3.8s | **2.0s** | **快 1.9 倍** |
| 退化率 | 0/8 | 0/8 | **无差异** |
| 答案质量 | `6` ✅ | `6` ✅ | 无差异 |

**两个写法等价**（`thinking:{"type":"disabled"}` 与 `reasoning_effort:"none"`），
**用前者** —— 它和 GLM 是**同一个写法、同一个报错格式**
（`expected struct ThinkingOptions`），意味着**一套代码通吃两家**。

### ⚠️ 一个必须记住的陷阱

| 写法 | HTTP | 看起来 | 实际 |
|---|---|---|---|
| `thinking:{"type":"disabled"}` | 200 | 正常 | ✅ **真生效** |
| `enable_thinking:false` | 200 | 正常 | ❌ **静默忽略**（`reasoning_tokens=14` 仍在推理） |
| `thinking:false` | **400** | 报错 | 类型错误，须用对象 |

> 📌 **`enable_thinking:false` 是最危险的那个** —— 返回 200、content 正常，
> **但思维链仍在跑**。这类「看起来生效实际没生效」的坑最难排查。
> **验收方式：查 `usage.completion_tokens_details.reasoning_tokens` 是否为 0，不能只看 HTTP 状态码。**

### 为什么关掉不只是为了省钱

思维链会引入「模型自己推理如何遵守约束」这一**混杂变量**，
而路线 1 要测的是**消息组装位置**的效果，不是模型的推理能力。

**附录 C.6 实测证实了这一点**：reasoning tokens 随轮次递增 ——
R1 多数较小（0–360），R3 施压轮冲到 1,210，R4 到 606。

> **它不是被 prompt 说服了，是在计算怎么绕。**

## 什么情况下要重审本决策

| 触发条件 | 重审什么 |
|---|---|
| **DeepSeek 端点出现长期不稳定** | 是否切换主基座（fallback 预案） |
| **GLM 免费额度耗尽** | 是否换成 DeepSeek 做调 prompt 阶段 |
| **真人素材场景上线** | 合规路径：本地化 / 显式授权 / 还是不上传 |
| **模型 ID 再次变更** | 检查 `.env` 的 `*_MODEL` —— **本项目已踩过一次**（2026-07-24 退役） |
| **单月 API 支出超过 ¥50** | 说明有失控调用，先查 `repeat` 和循环逻辑，不是先换模型 |
| **出现新的更强/更便宜的模型** | 走标准流程：改 `.env` 三行 → 跑一次复验（¥0.05） |

## 这个决策最脆弱的环节

**脆弱点：主基座的稳定性结论只有 48 次请求的样本。**

| 证据强度 | 项 |
|---|---|
| ✅ **强**（可复现、多组一致） | 缓存命中率 91%、关思维链省 7.3 倍、换模型零代码改动 |
| ⚠️ **中**（样本有限） | 「DeepSeek 比 GLM 稳」—— 0/16 vs 1/9，**量级差距大但绝对值样本小** |
| ❌ **弱**（未做） | 失控率的准确估计（需每组 20+ 次，见 E5 §A.7 #3） |

> 📌 **但即便是「中」强度的结论也足够支撑本决策** ——
> 因为**决策的代价很低**：如果将来发现 DeepSeek 不合适，改 `.env` 三行重跑一次即可。
> **低代价决策不需要高置信度的证据。** 这是本决策可以现在就定的根本原因。
