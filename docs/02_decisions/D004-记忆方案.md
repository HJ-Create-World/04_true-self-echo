# D004 · 记忆方案：结构化记忆 + 关键词触发（不用向量）

- **状态**：已采纳
- **日期**：2026-09-16
- **决策者**：HJ

---

## 背景

「让 AI 记住用户」的行业默认答案是**向量数据库 + RAG**：把记忆切块、embedding、存向量库、按语义相似度检索。

看起来是标准解法，但对这个项目有几个硬伤。

---

## 分析

| 维度 | 向量 RAG | 结构化 + 关键词 |
|---|---|---|
| 需要 embedding 模型 | ✅ 需要 | ❌ 不需要 |
| HJ 硬件能否本地跑 | ⚠️ 勉强，且要额外部署服务 | ✅ 无额外负担 |
| 记忆的形态 | 模糊的语义块 | 明确的事实卡片 |
| 可视化难度 | 高（向量是黑盒） | **低（卡片直接渲染成面板）** |
| 可解释性 | 低（为什么检索到这条？说不清） | 高（触发关键词一目了然） |
| 实现复杂度 | 高 | 低 |
| HJ 能否看懂 | 需要理解 embedding 概念 | ✅ 能 |

**关键判断**：

> 这个项目里的「记忆」不是模糊的语义搜索，是一批**结构化的事实**。
> 用户说「我妈生日是 3 月 12 号」—— 这是一条带字段的记录，不是一个需要语义检索的模糊片段。

而且 HJ 的明确诉求里有**记忆面板可视化**。向量检索的结果是一堆相似度分数，没法做成好看且有意义的面板；结构化卡片天生就能。

---

## 选项

| 选项 | 描述 | 后果 |
|---|---|---|
| A · 向量数据库 + RAG | 行业标准解法 | 需要 embedding 模型、部署复杂度高、黑盒、可视化难；且**引入了本项目不需要的新知识点** |
| B · 结构化记忆 + 关键词触发 | 记忆按类型存成卡片，靠关键词/实体匹配注入上下文 | 简单、可控、可视化友好；代价是检索能力弱于语义检索 |
| C · 全量塞进上下文 | 不做检索，所有记忆都塞进 Prompt | 上下文迅速爆炸，成本失控 |

---

## 决定

**采纳 B。** 具体设计：

| 项 | 设计 |
|---|---|
| 记忆形态 | 结构化卡片（类型 / 内容 / 触发词 / 时间 / 重要度） |
| 存储 | IndexedDB（本地） |
| 检索 | 关键词 + 实体匹配 + 重要度排序 |
| 注入 | 命中的卡片按重要度拼进 Prompt 的记忆区 |
| 容量控制 | 设上限，超限按「重要度 + 最近使用」淘汰 |

**这个选择抄的是 SillyTavern 的 World Info 思路** —— 一个被几十万人验证过的经典做法，不是新发明。

---

## 后果

**正面**
- 无额外依赖，不需要部署 embedding 服务
- 记忆面板可视化的难度大幅下降（卡片直接上屏）
- HJ 能完全看懂「为什么这条记忆被用上了」
- 符合「一个项目只学一样新东西」—— 本项目要学的是**人格结构化与演化**，不是 RAG

**负面 / 代价**
- 语义检索能力弱：用户说「那次我们去的那家店」→「那次」可能匹配不到
- 需要手工维护触发词，投料质量直接影响效果
- 记忆量大了以后，关键词匹配的噪声会上升

**缓解措施**
- 每张记忆卡片允许手动编辑触发词
- 注入时限制条数上限，避免噪声挤占上下文
- 如果未来真的不够用，**记忆层是独立的**，可以整体替换为向量方案而不动其他部分
