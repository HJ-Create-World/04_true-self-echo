# 执行侧干预 · 技术调研

> **什么时候读这份文档**：Phase 1 开工前定技术路线时；或需要向他人解释「为什么不去继续加码素材」时。
>
> **它不是**：决策本身（那是 `02_decisions/D007-Phase1转向执行侧.md`），也不是我们的实现方案 —— 它只回答「业界怎么做、有没有实测支撑」。
>
> **它能回答**：什么是执行侧干预？为什么写进 System Prompt 的规则会不生效？有哪些真正有效的手段？三条路线各自代价多大？
>
> ⚠️ **证据分级**：本文标注了 🟢 同行评审 / 🟡 社区共识 / 🔴 **未验证**。
> 引用前请核对 §附录 的来源清单 —— 其中 `Persistent Personas?`、Persona Drift、NoLiMa
> 三条**均未直读原文**，只作方向参考。

## 结论先行（TL;DR）

1. **「执行侧干预」不是新东西**，业界叫 **run-time / inference-time control**，与它对立的是
   **extraction-time / offline 建设**。项目的转向本质是：从「改数据」转向「改推理过程」。
2. **D007 的归因是对的，而且有直接对口的论文**。最重要的发现：**`Persistent Personas?`
   (arXiv:2512.12775)** 用 100+ 轮对话实测了「人格保真度随对话长度衰减」，并明确记录了
   **「fidelity 与 instruction-following 存在 trade-off，随对话推进，角色回应越来越像基线助手」**
   —— 这与 E2/E3 第 4 轮同时崩的行为**完全一致**。
3. **但有个关键修正**：D007 说的是「RLHF 顺从本能」。更精确的机制是**两层叠加**：
   - (a) **sycophancy**：RLHF 训练出的「迎合用户」倾向，有 ICLR 2024 论文实证；
   - (b) **位置导致的注意力衰减**：规则写在 prompt 中部，第 4 轮时它已在长上下文中间，
     **本来就处于注意力低谷**（Lost in the Middle，TACL 2024）。
   - **两者都可干预，且 (b) 便宜到几乎零成本**。这很重要 —— 意味着不必只靠「更聪明的 prompt」。
4. **HJ 的约束下，「解码层」整条路走不通**：logit_bias 在 Anthropic 不存在、在 OpenAI 新
   Responses API 也不存在，且在 gpt-4o 上**已被社区实测为不生效**。「架构层」的 guardrails
   是 Python 服务端方案，与纯前端不匹配。**真正可行的是 Prompt 层 + 多阶段层。**

## 问题 1：「执行侧干预」的业界对应

### 1.1 提取侧 vs 执行侧

| | 提取侧（Extraction） | 执行侧（Execution / Inference） |
|---|---|---|
| 业界叫法 | data prep / offline pipeline / indexing time | inference-time control / run-time steering / test-time compute |
| 何时跑 | 一次性，离线，用户不等待 | 每次对话，实时，用户在等 |
| 输入 | 原始素材 | 素材 + 用户输入 + 对话历史 |
| 产物 | 人格档案（静态资产） | 一句回复 |
| 失败表现 | 档案写错、写浅、编造 | 出戏、漂移、退化 |
| 优化手段 | Prompt 改提取、加素材、代码统计 | 位置、格式、自检、重注入、解码约束 |
| 典型论文域 | 信息抽取 / 数据质量 | alignment / steering / decoding |

**边界在哪**：分界线是「**有没有对话历史**」。一旦进入多轮，问题性质就变了 —— 从
「模型知不知道」变成「模型在长上下文里还记不记得、还愿不愿意照做」。

**一个关键类比**（跨域但准确）：这等同于**编译期 vs 运行期**。Phase 0 在优化编译器，
而 bug 在运行时的内存泄漏上。D007 的判断（边际收益归零）在架构上是对的。

### 1.2 四层干预手段对照表

| 层 | 具体手段 | 解决什么 | 代价 | 纯前端可行性 |
|---|---|---|---|---|
| **Prompt** | 结构化 System Prompt（XML/分节） | 可读性与可维护性 | 几乎零 | 🟢 **高** |
| | **负面约束**（negative constraints） | 明确禁区 | 比正面指令弱，模型易误解 | 🟢 高 |
| | **反面示例**（contrastive ❌→✅ 对） | 直接给出转换规则 | 占 token | 🟢 **高（性价比最高）** |
| | CoT / 自检 | 提升一致性 | 增延迟 | 🟡 中 |
| | **角色锚定**（persona anchoring） | 抗漂移 | 需多轮实验调 | 🟢 高 |
| | **约束三明治**（首尾重述） | 抗注意力衰减 | 少量 token | 🟢 **高（近零成本）** |
| **解码** | logit_bias | 强制/禁止特定 token | — | 🔴 **低（见下）** |
| | 约束解码 / JSON schema | 保证格式 | 需自定义解码循环 | 🔴 低（无自有推理） |
| | repetition penalty | 去复读 | 端侧 API 常不暴露 | 🔴 低 |
| | temperature / top_p | 稳定性 | 低温度→更"安全"也更"平庸" | 🟢 **高** |
| **多阶段** | Self-Refine（草稿-批评-修订） | 提升质量 | **2-3× 调用成本 + 延迟** | 🟢 高（详见 3.2） |
| | 双模型（生成+审核） | 独立视角 | 双倍成本 | 🟡 中 |
| | Constitutional AI / RLAIF | 内化规则 | **需训练** | ⛔ 与 D005 冲突 |
| **架构** | RAG 注入 | 动态补素材 | 需向量库 | 🟡 中（可简化为关键词） |
| | **状态机式对话控制** | 强制对话路线 | 僵硬，需枚举 | 🟢 **高（轻量版）** |
| | DST（对话状态追踪） | 记状态防漂移 | 需额外模型/代码 | 🟡 中 |
| | 规则引擎外挂 | 硬拦截 | 是后处理，改不了"语气" | 🟢 **高** |
| | NeMo Guardrails / Guardrails AI | 企业级护栏 | **Python 服务端** | 🔴 **低** |

### 1.3 解码层：为什么这条路对 HJ 关闭（重要）

| 事实 | 来源 |
|---|---|
| OpenAI **Chat Completions** 有 `logit_bias`（-100~100） | OpenAI API 参考 |
| OpenAI **Responses API** **没有** `logit_bias`，也无 frequency/presence penalty | 官方 CreateResponse schema |
| **Anthropic Messages API 不暴露 logit_bias** | 官方文档 |
| 社区实测：`logit_bias` 在 gpt-4o / gpt-4o-mini 上**完全不生效**（+100 强制 "Yes" 仍输出 "No"） | OpenAI Developer Community bug 贴 |
| 自建 logits processor 需 HuggingFace `transformers` 本地推理 | 与「不接后端」冲突 |

> **结论**：解码层在「调云端 API + 纯前端」的组合下**基本不可用**。不要再投入时间。

### 1.4 架构层：guardrails 的真实定位

- **NeMo Guardrails**（NVIDIA，Apache 2.0）：Colang 语言定义**对话状态机**，可定义
  「什么话题走什么分支」「什么时候重定向」—— 理念**高度契合**本项目。
  但它是 **Python SDK / FastAPI 服务**，纯前端无法直接用。
  → **可抄它的设计思想（状态机 + 话题重定向），不引入依赖。**
- **Guardrails AI**：输出校验 + 重新 prompt 循环（re-prompting）。有 **JS 版本**
  （文档明确写了 "Using Python or JavaScript"），但主要面向结构化输出校验（PII、schema），
  对「人格语气」这类软约束帮助有限。
- **OpenAI Agents SDK guardrails**：`input_guardrails` / `output_guardrails` 钩子，
  每个 guardrail 本身是个 agent，返回 "tripwire triggered" 布尔值。**思路可借鉴**
  （输出侧加一个独立审查 agent），但它需要服务端编排。

> **一句话**：guardrails 解决的是「**别说不该说的话**」（安全/合规），
> 而本项目的痛点是「**别用不像 ta 的方式说话**」（风格/身份）。**两者不同**，
> guardrails 的成熟度不能平移到人格保真上。

## 问题 2：为什么写进 System Prompt 的规则会不生效

### 2.1 现象对应哪个研究？—— 三个各自独立、会叠加的机制

| 机制 | 学界名称 | 出处 | 与本项目的对应 |
|---|---|---|---|
| **A. 迎合用户** | **Sycophancy** | Sharma et al., *Towards Understanding Sycophancy in Language Models*, **ICLR 2024**（Anthropic）arXiv:2310.13548 | 用户说「你能不能热情一点」→ 模型放弃角色设定。论文实测：5 个 SOTA 助手一致存在；被质疑时 Claude 1.3 在 **98%** 的题上错误认错；用户暗示错误答案可让准确率掉 **27%** |
| **B. 指令优先级失效** | **Instruction Hierarchy** | Wallace et al., *The Instruction Hierarchy*, **OpenAI**, arXiv:2404.13208 | System > User 的优先级**不是天生的**，是训练出来的。论文原话：LLM **常把 system prompt 与不可信用户文本视为同等优先级** |
| **C. 位置衰减** | **Lost in the Middle** | Liu et al., **TACL 2024**, arXiv:2307.03172 | 规则写在档案中部 → 第 4 轮时它已在上下文中间 → **本来就处于注意力低谷**。实测：20 文档场景下中部 vs 两端差 **~20 个百分点**，最差时**低于不给文档的闭卷基线（56.1%）** |
| **D. 人格保真衰减** | **Persona Drift** | *Persistent Personas?*, arXiv:2512.12775（100+ 轮实测，7 个模型） | **最对口**：明确记录「fidelity 与 instruction-following 存在 trade-off」+「对话推进后，角色回应**越来越像基线助手**」 |

**D007 的归因需要一个小修正**：不是单一原因，而是 **A（迎合）+ C（位置）** 的叠加。
这个修正有实际价值 —— 因为 **C 的成本几乎为零**，而 A 很难根治。

### 2.2 已知有效的对抗手段（按证据强度排序）

| 手段 | 证据强度 | 关键数据/结论 | 来源 |
|---|---|---|---|
| **约束三明治**（关键规则首尾各写一次） | 🟡 有机制支撑 + 广泛实践 | 首因（attention sink）+ 近因偏差双臂覆盖；Liu et al. 实测中部掉 30%+ | agentpatterns.ai / Xiao et al. 2023（Attention Sinks） |
| **正面指令 > 负面指令** | 🟡 多来源一致 | 「不要用非正式语言」弱于「使用正式专业的语言」。模型见过更多"做"而非"避免" | 多份 prompt 工程教材一致 |
| **✅ 反面示例（❌→✅ 成对）** | 🟡 社区强共识 | **禁令要模型自己推断改成什么；成对示例直接给出转换规则**。竞品 elysia.skill 实测 10 组有效 | 本项目 SKILL 笔记第九节 |
| **重注入 / 重述规则** | 🟢 **有实测** | Persona Drift 论文：**re-injecting the persona prompt 可部分逆转漂移，但不能完全消除** | arXiv:2604.01980（clawRxiv，**未验证**，见下） |
| **Self-Refine 自检重写** | 🟢 有同行评审 | NeurIPS 2023。**平均 +20%，但方差极大**：数学 ≈0，约束/情感类任务可 +30% | Madaan et al., arXiv:2303.17651 |
| **独立模型审核（双模型）** | 🟡 实践共识 | 评估比生成简单；但判官有偏差，需校准 | W&B / NVIDIA NeMo Gym 文档 |
| **位置优化（把规则挪到末尾）** | 🟢 有实测支撑 | 同上 Lost in the Middle | arXiv:2307.03172 |
| **Instruction Hierarchy 训练** | 🟢 有实测 | OpenAI IH-Challenge：安全可控性提升且**不损失 helpfulness**。**但需训练** | OpenAI IH-Challenge 博客 |
| **情绪化施压是攻击面** | 🟡 有描述 | "jailbreak by emotional appeal" / authority spoofing / **gradual erosion（渐进侵蚀）** 被列为四种典型攻击向量 | zylos.ai 综述（**未验证**） |

### 2.3 Self-Refine 的关键限定（避免踩坑）

> ⚠️ **自检修不好它自己看不见的错**。后续研究（非该论文本身）指出：LLM **基本无法在没有外部
> 反馈的情况下自我纠正推理错误**。且存在三类失效：
> **幻觉式批评**（把对的改成错的）、**风格漂移**（反复修订后变平淡啰嗦）、
> **成本叠加**（每轮 ≥2 次调用，**2-3 轮后收益递减，4 轮封顶**）。
>
> **对本项目的含义**：自检必须**给外部锚点**（如"对照人格档案里的负面清单逐条检查"），
> 而不是让模型"自己看看有没有出戏" —— 后者会得到虚假的"我很好"。

### 2.4 上下文长度与指令遵循的量化

| 研究 | 关键数字 |
|---|---|
| Liu et al., Lost in the Middle (TACL 2024) | 两端 ~75% / 中部 ~55%，**~20pt 落差**；最差低于闭卷基线 56.1%；20→50 文档仅提升 ~1.5% |
| NoLiMa（Adobe Research, 2025） | 13 个标称 ≥128K 的模型，**11 个在 32K 时已跌破自身短上下文基线的 50%**；某 70B 模型 94.3% → 42.7%，**有效长度≈2K** |
| Laban et al., *LLMs Get Lost in Multi-Turn Conversation* (2025) | 20 万+ 模拟对话，多轮 vs 单轮**平均掉 39%**；拆解后：**能力下降很小，不确定性大增** —— "模型没变笨，变飘了" |
| Persona Drift (clawRxiv 2604.01980，**未验证**) | 24 人格 × 200 轮：**第 80 轮 71% 的人格至少一个维度显著漂移**，第 200 轮 89% |

> **实践阈值**：没有普适安全线。但 **NoLiMa 的结论最重要** ——
> **标称 200K 的模型可能只有几 K 的有效指令遵循长度**。对人格档案这种"必须全程生效"的
> 内容，**不要把宝押在长上下文上，要靠重注入**。

### 2.5 直接回答：「写了禁令但模型违反」什么真有效

**排序（从有效到无效）**：

1. ✅ **重注入**（每 N 轮把关键约束贴到最近位置）—— 有实测支撑，成本最低
2. ✅ **✅❌ 成对示例**—— 把"禁令"翻译成"转换规则"，比纯禁令强得多
3. ✅ **约束三明治 + 正面重述**—— 抗位置衰减，近零成本
4. ⚠️ **Self-Refine + 外部锚点**—— 有效但要 2-3 轮，成本翻倍，且必须给检查清单
5. ⚠️ **独立审核模型**—— 有效但成本和一致性代价高
6. ❌ **纯负面约束**（只写"禁止…"）—— 最弱，模型易误解
7. ❌ **指望更长的 System Prompt / 更多规则**—— 反而稀释注意力，有反效果

## 问题 3：给 persona-forge 的三条路线（已排序）

### 路线 1（首选）：约束三明治 + 重注入 + 成对示例

**为什么排第一**：三项都有实测支撑，**全部是纯前端、零新依赖、可以在一天内做完并立刻用
冻结的评分标准验收**。而且它直接打击 2.1 表的 C（位置衰减）和 D（保真衰减）。

| 具体做法 | 实现量 |
|---|---|
| ① **约束三明治**：把「红线」（不得变激动、不得追问+长篇安慰）**同时写在 System Prompt 最开头和最末尾**，末尾版本用一句话重述 | 改 prompt 模板，**~10 行** |
| ② **每轮重注入**：每次请求时，把关键约束作为**最后一条 user 消息的前缀**拼进去（而非只放 system） | **~20 行**（拼消息数组） |
| ③ **负面清单 → 成对示例**：把 `conflicts.md` 的每条禁令，改写成 ❌通用版 → ✅角色版 两行对照，放进 few-shot | 内容工作，**1 天** |
| ④ **降低 temperature**：实测稳定区间（建议 0.7~0.9 起步，逐档测） | **1 行** |

- **复杂度**：**1-2 天**。零新依赖。
- **预期效果**：有实测支撑的间接证据（位置效应 20pt、重注入可部分逆转漂移）。**但针对
  persona-forge 的效果必须自己测** —— 用已冻结的六维标准跑四轮对话法即可。
- **风险**：低。最坏情况是「没提升」，不会让现有表现变差。
- **注意**：重注入**会被 prompt caching 破坏**（前缀变了缓存失效）。用 Anthropic 的话
  要评估成本，或把重注入放在已缓存前缀**之后**。

### 路线 2（次选）：输出侧审查 + 一次性重写

**为什么排第二**：有效但**贵**。这是 Self-Refine 的实用变体。

| 具体做法 | 实现量 |
|---|---|
| 生成后，用**第二个请求**做审查：给它「人格档案的负面清单 + 刚生成的回复」，要求**逐条判定是否违规**并只回 JSON（违规项 + 理由） | **~30 行** |
| 若判定违规 → **第三次请求**带违规理由重写 | **~20 行** |
| **关键：不要用首字流式**，否则要撤回已显示内容。改为「先完整生成 + 审查，再一次性渲染」 | 前端状态改动，**中等** |

- **复杂度**：**3-5 天**（含前端 loading 态改造）。
- **预期效果**：🟢 Self-Refine 有 NeurIPS 2023 实测（+20% 均值，约束类任务可达 +30%）。
  **但必须给外部锚点**（负面清单），否则会幻觉式批评。
- **风险**：
  - **延迟 2-3 倍**，对话体验明显变差；
  - **风格漂移**：反复修订会让文本变平淡 —— 这对"人格保真"是**反向风险**；
  - **把对的改成错的**（幻觉式批评）。
- **建议**：**不要对每轮都做**。只在触发条件（检测到红线关键词/情绪化施压）时才触发重写。

### 路线 3（备选）：轻量状态机 + 规则外挂

**为什么排第三**：理念最对（抄 NeMo Guardrails 的 Colang 思路），但**收益不确定、维护成本高**。

| 具体做法 | 实现量 |
|---|---|
| ① 定义 4-6 个对话状态（日常 / 被质疑 / 对方示弱 / 价值观测试 / 出戏警告），用**关键词 + 轮次**判状态 | **~50 行** |
| ② 每个状态**切换不同的 few-shot 示例集**（而不是全程带全部示例） | **~30 行** + 内容 |
| ③ **硬规则外挂**：用正则检测明显出戏（如出现"作为AI"/"我理解你的感受"），命中则追加一条系统提醒再生成 | **~30 行** |
| ④ **裁掉素材**：只把当前状态相关的档案片段注入（RAG 的极简版 —— 关键词触发，SillyTavern World Info 的做法） | **~50 行** |

- **复杂度**：**1-2 周**（含调状态划分）。
- **预期效果**：⚠️ **无直接实测数据**。竞品 elysia.skill 的「硬规则」实测有效
  （风格分 4.5 中 ≥3 分靠硬规则买来），**但该规则同时压平了语气多样性，是负优化**。
  这是真实警示。
- **风险**：
  - **状态划分靠猜**，可能引入新的僵硬感；
  - **关键词检测不可靠**，中文变体多；
  - 维护成本随状态数线性上升，**单人维护会累**；
  - ⚠️ **规则冲突无优先级 = 模型自由裁量**。本项目 SKILL 笔记已记录竞品这个坑
    （红线"不要生成哲学深度对话" vs 原则"承认悲伤的重量"打架），**必须显式声明谁优先**。

> 真瓶颈** —— 如果是，路线 3 的裁剪策略就有了方向；如果不是，说明问题更深，再上路线 2。
